## 5. RPO, cited (WP 9.1)

- **Cadence:** `backup-loop.sh` takes a backup at startup and then once a day at `BACKUP_HOUR_UTC` (default 02:00 UTC); WP 9.4's `pre-migrate-backup` adds one before any migration. So the worst case for losing the database at the instant before the next backup is 24 h of data, the RPO.
- **Alarm:** `docker/backup/healthcheck.sh` marks the container unhealthy when the newest successful backup is older than `BACKUP_MAX_AGE_SECONDS` (default 93,600 s = **26 h**: the cadence plus two hours of slack), and `GET /ops/backup-status` reports `backupOverdue` against the same 26 h (`DEFAULT_BACKUP_MAX_AGE_SECONDS`). The 26 h is the alarm threshold; the RPO the product promises is 24 h.
- **The rows (`docs/evidence/phase-9/wp9.1-soak.md` §8.3–8.5):** `ops_backup_runs` `ok` rows (a real `backup.sh` run: "verified 542032 bytes, 987 restorable object(s), schema_migrations present"); `GET /ops/backup-status` through Caddy: `lastSuccessfulBackupAgeSeconds` 36, `backupOverdue` false, then after the drill `lastDrillVerdict "pass"`, `drillOverdue` false; `ops_restore_drills` `pass`. ## 7. Decisions

- **D1 (item (j)) — load-conditional skips: yes, with a named reason, and never on a passing reading.** `apps/api/test/db/perf-support.ts` (header, and `perf-support.test.ts`): a reading inside its budget passes at any load; over budget on a host whose 1-minute load is below 3 **fails** (the machine was quiet, so the number is believed); over budget at 3 or more is the skip `HOST_LOADED`, with the reading and the load in the note. The two reds of the week were load (`GET /holdings` 354.6 ms at load ~7; reports 1,399 ms at load 7.99 against 37.8 ms alone): both now read 34.5 ms (load 1.34) and 39.9 ms (load 1.74) and pass. Why not "stay as they are": a red that cannot be believed trains everyone to re-run until green, which is how a real regression gets re-run away. Why not "skip before measuring above a load threshold": the load average is lagging and the test's own corpus load inflates it, and a pre-skip would be a green that measured nothing. The decision is sabotage-tested both ways (§8, S1, S2). Every file that can take the skip declares it (`// perf-skip: HOST_LOADED — …`) and `scripts/check-perf-skips.ts` lists each call site. After a corpus load the tests wait up to four minutes for the load to fall below 3 (`settleLoad`, which prints what it waited for), so a test does not time the load it just made.
- **D2 — a GitHub shared runner is not the target hardware.** The new timing assertions skip `ON_SHARED_RUNNER` (`CI` set), like `projection-perf.test.ts`'s since WP 4.13; the row-count tests and the corpus loads still run there. `nightly-perf.test.ts` on CI runs the whole chain at 30 days of backfill and a 250 ms poll, to fit the `migration-test` job's 25 minutes; its 730-day, shipped-interval run is the local one. `holdings-scale-perf.test.ts` (informational) does not run on CI at all.
- **D3 — the "04:00 chain" is driven by the real scheduler, in cron order, without sleeping.** The four schedule rows (`connections.nightly_sync`, `planning.net_worth_snapshot`, `insights.nightly`) are made due and `scheduler.tick()` is called, each stage waiting for the queue and the subscribed consumers to go quiet before the next; the ±20 minute jitter 08 §3.7 puts on the 03:15 sync is zeroed (`random: () => 0`; it is a deliberate delay, not work), and `connections.last_synced_at` is set 24 h back (Plaid's `minSyncIntervalSeconds` is four hours, and a scheduled sync inside it is skipped: the first draft timed eight skips). The orchestrator is the harness's (over the api pool); the worker's runner, pump and scheduler are on the worker's own, correctly sized pool.
- **D4 — "recorded-reply provider fake".** `FakePlaidApi` replaying pages shaped like the connector's recorded fixtures (the same transaction template and five-account item the conformance suite uses), pushed through the real exchange route and the real connector, rather than a second fake invented for timing.
- **D5 — transfer pairing is timed as its own step but is not a shipped job (P-2).** `pairTransfers` has callers only in `seed-loader.ts` and the confirm/reject route; no consumer or schedule runs it on a sync. The spec lists it in the chain, so it is timed (6.7 s over 20,801 legs) and labelled "direct call, not a shipped job".
- **D6 — print-only changes to existing perf files.** `planning-perf`'s numbers had never been visible (`console.log`); `ledger/test/perf.test.ts` and `projection-perf.test.ts` print the load; `phase2-reports-http-perf.test.ts` gained the row-count test it lacked (it asserted the dataset's length in `beforeAll`, not the database's); the two ledger-package files gained one `// perf-skip:` comment each so the check passes over the real tree. The budgets themselves are unchanged (200 / 150 / 800 ms).
- **D7 — the scale seed for (g).** `investments-perf.test.ts`'s 12 positions are the Phase 3 correctness seed; WP 4.13's scale seed (200 positions, five years of daily prices) had no holdings-route timing. `holdings-scale-perf.test.ts` is that, informational as the spec says.
- **D8 — RAM is measured from cgroups.** `anon` is the RSS a process holds; `memory.current` also charges page cache (578 MiB of it Postgres's on the first idle sample), so both are printed. The insights module is off until `advisor_token_secret` has content (RUNBOOK), so the idle sample and the nightly chain were taken with it ON as well (it did not change the idle RSS).
- **D9 — seeding the stack.** The 50k corpus was loaded into `pf-perf` through `loadSeedDataset`, whose four bulk `TransactionsUpserted` events (50,040 rows between them) and 2,737 `TransferPaired` events kept the worker's consumers busy for 19+ minutes without finishing the first (P-4); before any final number the consumers' offsets on that scratch database were set to the head (`UPDATE event_consumer_offsets …`, `pf-perf` only) so the stack was idle. The pump's throughput is measured, honestly, by `nightly-perf.test.ts`'s 500-row Plaid pages.

## 9. Open items, regressions and findings in other packages (reported, not fixed)

- **P-1 (HIGH for the nightly budget) — the job runner wakes late.** `packages/platform/src/jobs/runner.ts` `claimLoop`: after a job finishes, if no _eligible_ job remains (here `insights.run`'s per-kind `concurrency: 1`, `packages/contexts/insights/src/jobs.ts:185`), the loop waits `listener?.wait(pollIntervalMs)`; only an _enqueue_ notifies the listener, a job completion does not. So a kind capped at one runs **one job per `JOB_POLL_INTERVAL_MS`** (5 s, `compose.yml:489`), however short the job. The nightly `insights.run_all` fans out 40 `insights.run`: **197.9 s** of the 243.4 s chain at 730 days, against **6.6 s** of handler work (`job_runs`), and **14.7 s** with `PERF_NIGHTLY_JOB_POLL_MS=250` (the same code, 60-day backfill). Every advisor added costs 5 s; the 5-minute budget is passed here with a 57 s margin and will not stay passed. Fix, for whoever owns the runner: wake the claim loop when a job completes (`sleeper.wake()` / a notify in `execute`'s `finally`), which would take the insights stage to its ~7 s of work. The evidence number: `nightly.log`, `jobWork`.
- **P-2 — transfer pairing is not part of any shipped nightly chain** (`pairTransfers` callers: `seed-loader.ts`, `routes/transactions.ts` confirm). Master plan 04 §4.2 lists nothing that pairs; the dispatch's chain does. Either a consumer/job is missing or the chain description is wrong.
- **P-3 — the api healthcheck's `start_interval`** (§3, §8 item 3).
- **P-4 — the consumer pump's throughput on a bulk event.** Loading the 50k corpus with `loadSeedDataset` produced four `ledger.TransactionsUpserted` events carrying the 50,040 rows and 2,737 `ledger.TransferPaired`; the real worker (categorization, recurring) had committed **nothing past the first small event in the 19 minutes after the first big one** (event seq 8 recorded 00:36:23, still open at 00:55; one core at 98 %), and the budgeting consumer handled about one `TransferPaired` per second. In the other direction the 730-day Plaid backfill (500-row pages, so smaller events) took 584 s for 20,752 rows end to end, about **35 rows/s**, almost all of it in the consumers (the vitest worker at 98 % of a core for 8+ CPU-minutes after the last sync job had finished). 09 §5.3 asks 250k rows recategorised in under 60 s; this is two orders of magnitude off that row (not gated here; 9.14 should know). The consumer pump holds one transaction open per batch, so a batch cannot show progress.
- **P-6 — `GET /holdings` and `GET /investments/allocation` over the 200-position scale seed read ~2.0 s** (p50 1,961.9 / 1,945.6 ms, p95 2,043.1 / 2,009.8 ms at load 1.5; 34.5 / 31.5 ms over the 12-position seed). `apps/api/src/routes/investments.ts` `priceHoldings` awaits one `reader.price(securityId, asOf)` **per security, in sequence** ("One price lookup per security, not per holding"): 200 sequential walks of 07 §6.1's ladder, each several round trips, about 9.8 ms per security here against 2.9 ms per security at 12 (the `prices` table is 365,000 rows, so each ladder rung is also slower). It is O(positions) in database round trips and both routes (and every route built on `portfolioFor`) pay it. The 200 ms budget those routes meet at 12 positions is missed tenfold at the scale the plan sizes the product for; §3.4 names no budget for them, 09 §5.3 none either (the dashboard does not call them), so this is recorded, not red. **Root cause, measured:** `packages/contexts/investments/src/prices.ts` `drizzlePriceStore.observationsOnOrBefore` (lines ~335–357) selects **every** `prices` row for the security on or before the date, `ORDER BY price_date DESC`, with no `LIMIT`, and the reader keeps the newest; on the scale seed that is 1,826 rows per security and 365,000 rows per request (every row of the table), each parsed into a JS object. `holdings-scale-perf.test.ts`'s profile prices the first N securities with the route's own `priceHoldings` (median of five): **N = 1: 10.1 ms, N = 10: 101.4 ms, N = 50: 484.1 ms, N = 200: 1,910.5 ms (9.55 ms per security, perfectly linear)**, against `readHoldings` at **5.2 ms**. Fix, for the investments owner: bound the read (a `LIMIT` at the ladder's carry-forward window, or `DISTINCT ON (source)`), or fetch every security's newest observations in one query.
