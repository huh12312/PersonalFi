# WP 10.15: The block kit (V8 of the visual programme)

**Request (Chris, verbatim):** "Dispatch v1 and once complete continue thru v8", following "i really like the visuals within monarch money when it comes to spend tracking and other financial health … identify strategic visual improvements to more formally mirror it." V8 is the eighth and last item in §3 of `docs/research/10-visual-design-notes.md`. Its sources are Monarch's server-driven report blocks (`GetReportsData`) and its insight fields (§1.4).

**Result.**

- **The vocabulary.** A typed, versioned block vocabulary (`contractVersion: 1`, fifteen kinds) lives in `@core/kernel` and is published in the OpenAPI document as `Block` / `BlockDocument`.
- **The schemas.** Both sides validate with Zod: the API's schema and the web's are built from the same kernel parts and run one shared fixture corpus.
- **The renderer.** It has one component per kind and wraps the existing components (`BudgetMeterRow`, the Cash Flow bar row, `NetWorthStackedChart`, `NarratedSummary`, `Money`, `Badge`). Every chart block has its table, and a Blocks gallery sits on `/dev/kitchen-sink` in both themes.
- **Reports.** Spending, Income and Budget vs. actual are drawn from `GET /reports/blocks/*`. Those routes call the same function as the report routes, and an api-db test compares them figure for figure on the categorised 50k demo seed. The Sankey stays bespoke.
- **The Brief.** It renders an overview (the week, ranked actions by dollar impact, milestones, the health card) and each card's body as blocks. A narration is a `text` block with `role: 'narration'` drawn through `NarratedSummary`, so the provider and model badge is kept.
- **The narrator payload is untouched.** The payload builder's files show no diff, and an api-db test proves the envelope is byte-identical before and after the Brief and its blocks are served.
- **Insight cards** gain entity mentions that link only when the insight's own evidence cites the entity, a context line, a value line, a persisted bookmark with a Bookmarked filter, and Helpful / Not helpful. Not helpful reuses the dismiss-reason dialog for the reason. The new columns come from the expand-only migration `0051_insight_feedback.sql`.

**State of the tree.** Uncommitted, on `main` at `1ea92c5` (the orchestrator's execution-log commit, which touches none of this WP's files). Nothing is staged. One expand-only migration (DDL in §5). No new dependency and no lockfile change. The 16 PNGs that are not this WP's (`wp10.3-*` modified, `wp3.11-*` untracked) are untouched. This WP adds 12 `wp10.15-*.png`.

**How it was built.** The orchestrating agent wrote the contract: the kernel vocabulary, the API schema, the builders, the routes, the api tests, the docs, the e2e and this file. Two forks of it then ran in parallel. Fork W built the web renderer, the gallery, and the Reports and Brief screens. Fork I built the insights bookmark, feedback and mentions work end to end. Their reports are folded in below.

**Not done, by design.**

- **No saved-report store exists.** Reports has four fixed sections, so the block routes serve the three that are not the Sankey: `GET /reports/blocks/spending`, `/income` and `/budget-vs-actual`. Nothing called `/reports/saved/:id` was invented.
- **The Sankey is not a block** (the dispatch).
- **The insight cards are not blocks.** They gained their structure as fields (`titleSegments`, `bodySegments`, `contextLine`, `mentions`). Their chrome is interactive (bookmark, feedback, accept, dismiss, the evidence panel), and blocks are display-only.
- **Merchant mentions never resolve.** A merchant reaches an advisor as a one-way `MERCHANT_` pseudonym (D22, `snapshot/tokens.ts`), and reversing it would need a reversal table. The vocabulary and the web support the kind (`/transactions?merchantIds=`).
- **"Saved $Y so far" is not built.** No field records a captured value. The value line is "Worth $X / year" or "Worth $X one-time", and it is absent when the insight claims nothing.
- **Feedback does not feed the advisor policy.** Helpful / Not helpful is state on the row. The cooldown ladder, quarantine and rule health still read only the dismiss path (`insight_feedback`, the action log).
- **The Bookmarked filter filters the pending feed**, so a bookmarked insight that has been accepted is not listed.
- **`sparkline-row` does not wrap the Health `Sparkline`.** That component plots by calendar day, and a block carries values only. The row draws the same mark spec by position and prints "From X to Y", never a computed change.
- **`pie` is a small visx donut,** not `AllocationDonut`, which is tied to its allocation report and textures. It has a legend with each value and a table, and no total or percentage.
- **The Brief overview's counts** ("Ranked actions", "Needs attention") count the items the route serves. They are not money and add no figure.

**The rules, mechanised** (`docs/design/blocks.md`):

- Every object is strict, and every colour field is an enumeration of hue or role names.
- Money is integer minor units in a string.
- An href matches `BLOCK_HREF_PATTERN`: in-app, never `//`, never a scheme, never a backslash.
- `amountMinor: null` and `value: null` require `withheld`.
- A meter at `"0"` must be `no_budget`.
- A stacked bar's `total` must equal the sum of its own segments.
- A table row has one cell per column.
- A narration block carries its `narration`, and only a narration block does.
- The server refuses an unknown kind; the web draws "Unsupported block (kind)", or "Invalid block (kind)" for a known kind that breaks a rule. A document of another `contractVersion` is drawn as unsupported, in words.

**Where the schemas live, and why there are two.** `zod` is resolvable from neither `packages/kernel` nor `packages/contracts`: pnpm does not hoist, and adding the dependency is a lockfile change. So the kernel holds the parts and the two Zod schemas are built from them: `apps/api/src/blocks/schema.ts`, which is on the wire, and `apps/web/src/components/blocks/schema.ts`, typed against the generated `Block`. Both run `BLOCK_FIXTURES`: 19 valid blocks, every kind at least once, and 18 refusals.

### 1.2 Server

- **`apps/api/src/blocks/hrefs.ts`.** `transactionsHref` writes the `/transactions` search the way the router reads it (arrays as JSON). `categoryHref` points at V7's screen, with `?month=` when given.
- **`apps/api/src/blocks/reports.ts`.**
  - `categoryMonthBlocks` gives one `stacked-bars` block per currency: a bar per month, a segment per non-zero cell with its magnitude, its count, its drill-through `href` and `labelHref` to `/categories/:id?month=`. No cells gives the screen's sentence instead.
  - `budgetVsActualBlocks` gives one `table`: the name linking to the category, Assigned / Activity / Available as the route's money, overspend as Cash / Credit badges, and a transactions link.
- **`apps/api/src/blocks/brief.ts`.**
  - `briefItemBlocks` gives a card's blocks: the body text (narration-badged whenever a narration exists or is expected: shown, withheld under R-2, or pending), the headline money figure or `withheld: 'No dollar figure…'`, and the carried badge.
  - `briefOverviewBlocks` gives the overview:
    - the week;
    - the ranked actions as bar lists, one per kind of figure and currency, so yearly and one-time figures never share a scale, and items with no figure are named in a caption rather than drawn;
    - undismissed net-worth milestones (newest three, with a link to the dashboard);
    - the health card: the score from `findLatestHealthScore`, withheld with the same words the old card used, plus the link.
- **`routes/reports.ts`.** The spending, income and budget-vs-actual handlers were refactored into `categoryMonthCells` and `budgetVsActualOf`. The report routes and the new block routes call these same functions, so the two cannot drift.
- **`routes/brief.ts`.** `AdvisoryBrief.blocks` and `BriefItem.blocks` are `BlockDocument`s, built after serialisation from the served fields (`withBlocks`) plus `overviewReadsFor`, which reads the health score and the milestones (`@ctx/planning`).
- **`routes/insights.ts`** (Fork I).
  - The `Insight` wire gains `bookmarkedAt`, `feedback`, `feedbackReason`, `mentions[{text, entityType, entityId, evidencePosition}]`, `titleSegments`, `bodySegments` and `contextLine`.
  - New routes: `POST /insights/{insightId}/bookmark` and `POST /insights/{insightId}/feedback`. A reason without `not_helpful` is a 400; a foreign or unknown id is a 404.
- **`@ctx/insights`** (Fork I).
  - `src/bookmarks.ts`: `setInsightBookmark` and `setInsightFeedback`, each scoped by `user_id` and `id`.
  - `src/mentions.ts`:
    - `mentionCandidatesOf` admits only `snapshot:` refs whose leaf is `category_ref`, `account_ref` or `transaction_ref` and whose resolved value is a UUID.
    - `segmentText` matches the longest name first and is case-sensitive.
    - `contextLineOf` gives "About Groceries, Checking · transaction 1 … and N more".
  - Names come from `listCategories` and `listAccounts`. An id with no name is dropped, never invented.

## 5. Migration DDL (`packages/db/migrations/0051_insight_feedback.sql`)

```sql
ALTER TABLE insights
  ADD COLUMN bookmarked_at TIMESTAMPTZ,
  ADD COLUMN feedback TEXT
    CONSTRAINT insights_feedback_check
    CHECK (feedback IS NULL OR feedback IN ('helpful', 'not_helpful')),
  ADD COLUMN feedback_reason TEXT
    CONSTRAINT insights_feedback_reason_check
    CHECK (feedback_reason IS NULL OR feedback_reason IN (
      'NOT_TRUE', 'ALREADY_KNOW', 'NOT_ACTIONABLE', 'DONT_CARE',
      'WRONG_AMOUNT', 'INTENTIONAL', 'LATER'
    )),
  ADD CONSTRAINT insights_feedback_reason_requires_not_helpful
    CHECK (feedback_reason IS NULL OR (feedback IS NOT NULL AND feedback = 'not_helpful'));
```

The file also adds a `COMMENT ON COLUMN` for each of the three columns.

- **No equivalent columns existed.** `insight_feedback` is the append-only action log (accept, dismiss, snooze, reopen), so 0051 adds state on the row and writes nothing new to the log.
- **A bug the db test caught.** The first version of the last CHECK was a bare `feedback = 'not_helpful'`. That evaluates to NULL when `feedback` is NULL, and a CHECK lets NULL through. It was fixed before the file was used anywhere but scratch databases.

## ORCHESTRATOR
