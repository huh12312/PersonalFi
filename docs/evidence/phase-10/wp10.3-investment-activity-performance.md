# WP 10.3: Investment activity, and performance by account and by who manages it

**Request (Chris, verbatim):** "Dispatch that enhancement. I want to track investment performance inclusive of those transactions in the investment tab. Without it I can't maintain a financial health/wellness snapshot nor how my advisors, robo advisors, and self directed is performing."

**Result.** Investments has an **Activity** tab listing every investment movement Plaid's `/investments/transactions/get` brought in (buy, sell, dividend, reinvested dividend, interest, contribution or transfer in, withdrawal or transfer out, fee, tax, split, other), filterable by account, type and dates, keyset-paginated, and saying "a sync is pending" — not "no activity" — for an account whose investment leg has never run. An investment account's settings carry **Managed by** (advisor, robo-advisor, self-directed; migration 0042). The **Performance** tab measures the whole portfolio, one account, or each management class side by side, under a **health snapshot** (value, net contributions, dividends and interest, fees, gain over the period; the TWR and its annualization status in a separate block). And the point of the package: **what counts as an external flow** is now decided from the provider's own subtype, not the lot engine's house type — which fixes six classes of mis-counted Plaid movements (§4), including the one that matters most for a 401(k): a payroll contribution reported as `buy/contribution` was being counted as investment growth.

**State of the tree.** Uncommitted, on `main` at `6a5f3b6`. Nothing staged. Migration `0042_account_overrides_management.sql` is expand-only (one nullable column with a CHECK; the row-not-empty CHECK re-declared wider; see §5 item 1).

**Not done by this WP, by design.** No live Plaid call: everything Plaid-shaped runs over the recorded Sandbox fixture through the hermetic `FakePlaidApi`. Chris's first look at his own Sandbox 401(k) (mask 6666) and IRA (5555) after `just upgrade` is the live check. No backfill: classification happens at read time, so rows stored before this WP are classified correctly without one, and the next sync's re-fetched window refreshes their stored `type` through the existing upsert. `~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets were not read, listed, built or touched. No compose stack was started (the tests used the already-running dev database on `127.0.0.1:5433` through their own scratch databases, as WP 10.1 did), so there was no `-p wp103` stack to take down.

## 4. The flow audit (deliverable 4)

`readFlows` took `type IN ('CASH', 'TRANSFER_IN', 'TRANSFER_OUT')`. Through `normaliseTransactionType`, Plaid's documented pairs land as follows (before this WP):

| Plaid type/subtype                                                                         | House type (before)                       | Counted as a flow before?                               | Correct                              |
| ------------------------------------------------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------- | ------------------------------------ |
| `cash/contribution`                                                                        | `CASH`                                    | yes (+)                                                 | yes                                  |
| `cash/deposit`, `cash/withdrawal`                                                          | `TRANSFER_IN` / `TRANSFER_OUT`            | yes                                                     | yes                                  |
| `cash/dividend`, `cash/qualified dividend`                                                 | `DIVIDEND`                                | no                                                      | no (income)                          |
| `cash/interest`                                                                            | `INTEREST`                                | no                                                      | no (income)                          |
| `fee/account fee`, `fee/management fee`, `fee/transfer fee`                                | `FEE`                                     | no                                                      | no (cost)                            |
| **`cash/long-term capital gain`, `cash/short-term capital gain`, `cash/unqualified gain`** | `CASH`                                    | **yes — a fund distribution counted as a contribution** | no (income)                          |
| **`cash/tax`, `cash/tax withheld`, `cash/non-resident tax`**                               | `CASH`                                    | **yes — a tax counted as a withdrawal**                 | no (cost)                            |
| **`cash/margin expense`**                                                                  | `CASH`                                    | **yes**                                                 | no (cost)                            |

The fix is both halves the brief allowed: the **filter** is now `classifyActivity` (the provider's subtype decides what the house type cannot), and the **mapping** sends capital-gain distributions to `DIVIDEND` and margin expense to `FEE` so the stored type is truthful for new rows (the upsert refreshes `type` on re-sync).

## 5. Decisions and deviations, stated

1. **0042 drops and re-adds one constraint.** The brief said "nothing dropped". `account_overrides_not_empty` (0035) requires one of the three old fields, so without re-declaring it a holder could not save _only_ "Managed by". Postgres has no ALTER for a CHECK expression, so the widening is a `DROP CONSTRAINT` + `ADD CONSTRAINT` of the same name in the one migration transaction — 0029's shape for `snapshot_grants_scope_check`. Every row valid before is valid after; no data is touched. Sabotage S12 shows the widening is load-bearing.
2. **The period summary is a fourth disjoint object.** The brief listed value, net contributions, dividends and interest, fees as flat fields of each by-management row. They are under `summary` (a `PeriodSummary`, `kind: 'period_summary'`, with `?: never` guards against `periodReturn`, `annualized`, `timeWeighted`, `benchmarkComparable`; the TWR wire gained `periodGain`/`netContributions`/`closingValue` `?: never`), and the same object is the health snapshot on `/investments/performance`. "Value at `to`" is `summary.closingValue`.
3. **Two dollar gains, named apart.** `dollarGain` stays what it was (unrealized gain over today's positions against cost basis, now scoped). The health snapshot's dollar gain is `summary.periodGain` = closing − opening − net contributions: "the change in value that did not come from your own money", which is the figure a period snapshot needs.
4. **`tax` is an activity kind** beyond the brief's list: a tax withheld is a cost, but calling it a fee would overstate fees.
5. **Reinvested dividends are reported apart** from "dividends and interest": a broker that reports both the cash dividend and the reinvestment buy would otherwise count one dividend twice.
6. **An unrecognised cash movement is now excluded and named** (`unclassifiedMovements`), where the old filter counted any `CASH` row as a flow. Neither "contribution" nor "nothing" can be known from `cash/pending credit`.
7. **`flow` on each activity row** (not in the brief): the external flow the performance route used, so the Activity list and the return cannot disagree about a 401(k) contribution-buy's sign.
8. **"Sync pending" comes from `sync_runs`**: the `investment_txns` leg's runs for the account's connection. `INVESTMENT_ACTIVITY_PROVIDERS = ['plaid', 'coinbase']` (the two manifests declaring the capability) decides that an account from any other provider is `not_applicable` rather than pending.
9. **By management with the health snapshot**: the snapshot above the comparison is the whole portfolio's (each class's dollars are in the comparison's own table).
10. **Mock handlers**: the investments screen's routes live in `mock-investments.ts` (its existing mock, the one the a11y sweep layers); `mock-api.ts` gained empty answers for the two new routes.

### Residuals

- A provider that reports **both** a `cash/contribution` and a `buy/contribution` for the same payroll money would be counted twice. Not seen in the fixture or Plaid's documentation; the Activity list would show both rows.
- A crypto self-transfer between two of the holder's own accounts is external to each account and nets to zero across the portfolio only when both legs are valued; otherwise it is named in `unvaluedTransfers`.
- Rows synced before upgrade keep their stored `CASH` type for capital-gain distributions until a sync re-fetches them; their **classification** is right immediately (read-time), only the stored `type` column lags.

## 6. The migration's DDL

```sql
ALTER TABLE account_overrides
  ADD COLUMN management TEXT
    CONSTRAINT account_overrides_management_check
    CHECK (management IN ('advisor', 'robo_advisor', 'self_directed'));

ALTER TABLE account_overrides
  DROP CONSTRAINT account_overrides_not_empty;

ALTER TABLE account_overrides
  ADD CONSTRAINT account_overrides_not_empty
    CHECK (tax_treatment IS NOT NULL OR role IS NOT NULL OR valuation IS NOT NULL
           OR management IS NOT NULL);

COMMENT ON COLUMN account_overrides.management IS
  'Who manages the account: advisor | robo_advisor | self_directed. NULL = unclassified (the holder has not said; never inferred). Groups GET /investments/performance/by-management. Moves no projection. WP 10.3.';
```
