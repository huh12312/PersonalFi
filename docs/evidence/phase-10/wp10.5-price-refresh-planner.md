# WP 10.5: The price-refresh planner, Refresh now, USD bare tickers through OpenFIGI (D29), and a project-scoped dev volume

**Request (orchestrator, from WP 10.4 §0 defects (f) and (g) and the WP 10.4 dev-volume incident):** build the planner the nightly refresh never had, a "Refresh prices" action, the USD bare-ticker OpenFIGI tier recorded as D29, and scope `compose.dev.yml`'s data volume to the compose project.

**Result.** The nightly refresh now prices what the holder owns: every security with a non-zero position, read once through `@ctx/investments`' new `readPricingPositions`, routed by `securities.type` through `PROVIDER_FOR_KIND` (Tiingo by ticker; CoinGecko by coin id from WP 3.4's native-asset map), with an FX pair through FRED for every non-USD position currency. A security whose subject cannot be built (no ticker, a token with no coin id) is named with its reason; cash, bonds and "other" are counted and never sent. `worker.ts` needs no line of its own: an absent `planFor` now means the real planner. **Refresh prices** (`POST /market-data/refresh`, a button on the Investments header and in Settings, Market data) runs the same function at once, one run per holder per ten minutes (409 `market_data.refresh_too_soon`, `Retry-After`), and says what happened in words ("Priced 12 of 13; 1 unpriced: no CoinGecko key."). A saved key's card says "Holdings sync and price refresh use this key from the next run; use Refresh prices to fetch now." Building the planner exposed two more defects that would have made it price almost nothing: Tiingo and FRED were each asked for exactly one day (§0 (h), (i)); both now look back for the latest observation in one request. **D29**: a USD equity/ETF/mutual-fund bare ticker with nothing stronger is sent to OpenFIGI as a US composite job and establishes identity only on exactly one composite FIGI (§5); the D29 agent also fixed two older resolver defects it exposed (§5, please read). `compose.dev.yml`'s data volume is scoped to the compose project (§4).

**State of the tree.** Uncommitted, on `main` at `1c112db`. Nothing staged by this WP. No migration. New untracked files: `apps/api/src/price-refresh.ts`, `packages/contexts/investments/src/pricing-positions.ts`, `docker/dev-db/pgdata.yml`, `docker/dev-db/projects/personalfi-dev/.env` (un-ignored in `.gitignore`; a commit must add it or the dev project renders a new, empty `personalfi-dev-pgdata`), the tests and web files listed in §1, §5 and §6, and four `wp10.5-*.png`.

**Not done by this WP, by design.** No live call to Tiingo, FRED, CoinGecko or OpenFIGI: every provider is `createFakeTransport` under the real adapters (or `createFakeFigiMapper` for the resolver), with a fixed public DNS answer. **Chris's first Refresh prices is the live check.** No database was brought up: every db test used the running `personalfi-dev-db-1` (127.0.0.1:5433) through the harnesses' own uniquely named scratch databases (new suites named `wp105refresh`, `wp105ustick`, `wp105ustamb`; the existing suites keep their own `personalfi_<ctx>_…` names), each dropped on close. The rate limit is held in the api process's memory (one api process per install): a restart forgets it, which costs at most one extra run, and every run still spends against the durable per-provider budgets primed from `market_data_runs`.

### Why the compose design is an include and not one interpolated name

Compose interpolation has `${VAR:-default}` / `${VAR:+alt}` and nothing else: no substitution, no comparison (probed on Compose 5.5.1: `${COMPOSE_PROJECT_NAME/-/_}` is "invalid interpolation format"). The dev project is `personalfi-dev` (a hyphen) and its volume `personalfi_dev_pgdata` (underscores), so no expression over `COMPOSE_PROJECT_NAME` yields the existing name for that project and a scoped one for every other. The one per-project switch Compose has is a file: an include's `env_file` defaults to the `.env` in its `project_directory`, which may be interpolated and may not exist. The scoped default uses a **hyphen** (`<project>-pgdata`) because the test caught that Compose's own `<project>_pgdata` spelling renders `personalfi_dev_pgdata` exactly for `-p personalfi_dev`. The volume key stays `pgdata`, so the db service's mount, its config hash and the hardening gate's `pgdata:db` allowance are unchanged; `compose-hardening-check.sh compose.dev.yml` passes (3 services, 0 violations, 4 documented exceptions). The running `personalfi-dev-db-1` was not restarted, recreated or stopped; only `config` was run.

### 5.Two pre-existing identity defects found and fixed in `resolver.ts`

1. **Upgrade-map key collision.** `resolveAll` keyed OpenFIGI answers on `idType:idValue` alone, and `figiUpgradeOf` re-derived a job from _every_ identifier of a fact. The result: a bare `VTI` (any currency) in the same batch as `VTI@XNYS` inherited XNYS's FIGI and resolved, and `BHP@XASX` and `BHP@XNYS` got the same (last-written) FIGI and merged. Answers are now keyed on the whole job (type, value, MIC, exchCode), and each fact reads only the answer to its own planned job. Red-first: `a bare ticker never inherits the FIGI another fact's MIC-qualified ticker was mapped to` failed on the unchanged resolver with `AssertionError: expected 'resolved' to be 'unresolved'`.
2. **A bare ticker could _find_ a row.** `resolveOne` built candidates from every matched key, so an attached bare-ticker key found the row, both in the no-identity branch (it resolved) and as a merge candidate. D29 attaches bare tickers to the rows it establishes, so a CSV's CAD `VTI`, never sent to OpenFIGI, resolved onto the US VTI row. That contradicts "non-USD bare tickers stay `unqualified_ticker`". Now only identity-bearing names and the provider's own (proprietary) id may find a row; the insert-race re-read uses the same filter. Red-first: `a non-USD bare ticker from another provider does not land on the row a USD one established` failed with `AssertionError: expected 'resolved' to be 'unresolved'`. This changes WP 3.1 behaviour. Every existing investments / investments-db / api-db test stayed green.
