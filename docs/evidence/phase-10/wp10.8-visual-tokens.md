# WP 10.8: Colour and chart tokens (V1 of the visual programme)

**Request (Chris, verbatim):** "Dispatch v1 and once complete continue thru v8" — after "identify strategic visual improvements to more formally mirror [Monarch]". V1 is §3's first item of `docs/research/10-visual-design-notes.md`: the foundation every later package reads.

**Result.** PersonalFi's colours now come from one generated source. The Radix Colors scales (MIT, 3.0.0, vendored: `sand` and the thirteen hues, light and dark, 12 steps each) sit under a layer of semantic roles (surfaces, text, borders, four status quartets, seven chart roles, thirteen chart fills, 52 chart-event roles), generated by `node scripts/gen-tokens.ts` into `tokens.css` (what the browser reads) and `tokens.ts` (a typed object for canvas/SVG code and tests). Every pre-existing token and Tailwind utility still exists, as a name for its role, so this is a re-plumbing: surfaces and chart chrome moved onto `sand` steps within ΔE 2 (OKLab ×100) of what they were, and text, brand, money and the legacy status colours kept their values as named off-scale house values, because the nearest step would be a visible repaint (§1.2). One contrast failure the move caused was fixed by moving a step (`--status-critical`, §1.2). Every category has a **stable, persisted hue** (`categories.hue`, migration 0045, seeded on first read by a hash of its id, editable by `PATCH /categories/{id}`, round-tripped by export/import), and account types have a fixed hue in code. Every chart reads the roles; the category charts and the allocation donut now draw in the thirteen fills, in an order found by exhaustive search that clears the dataviz skill's adjacent CVD (ΔE ≥ 10.3) and normal-vision (ΔE ≥ 20.5) floors in both themes.

**State of the tree.** Uncommitted, on `main` (dispatched at `976641d`; HEAD is now `d185d62`, the orchestrator's execution-log commit, which touches none of these files). Nothing staged by this WP. Migration `0045_category_hue.sql` is expand-only (DDL in §5). No new runtime or dev dependency; no lockfile change.

**Not done by design.**

- **No swatch picker.** There is no category _editor_ in the web app (only `CreateCategoryDialog`), so per the brief the picker is left for **V7** (the category detail screen). The API side is done: `PATCH /categories/{id}` accepts `hue`.
- **Badge and the legacy status tokens are not moved onto the status quartets.** `--status-good` is ΔE 7.5 from the nearest green step; moving `Badge` onto `--status-success-*` repaints every badge. The quartets exist and are contrast-tested; V4 (budget meters) is the first consumer and moves Badge with it.
- **Text, brand accent, money and destructive colours stay off the scales** (named house values with the reason beside each in `roles.ts`); see §1.2.
- **The 13-hue palette cannot pass all-pairs**, and four of its hues are under the chroma floor at every in-band step (§1.4). Recorded, not hidden.
- `~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets were not touched. The database work ran on the running dev database with scratch databases prefixed `wp108_` (§2).

What this means, stated plainly:

- **Chroma.** Radix's brown and mint (both themes) and lime and yellow (dark) have no step inside the lightness band at chroma ≥ 0.10; the rule "fix by moving the step" has no step to move to. They are kept because the brief and Monarch's palette name them; `CHROMA_EXEMPT` in `fills.ts` names exactly these, and `tokens.test.ts` fails if any other fill drops under the floor.
- **All-pairs.** The skill says no order of more than three hues passes all-pairs; thirteen certainly do not. A category's hue comes from a hash, so two categories drawn side by side can be any two hues, including the same one (there are more categories than hues). Identity therefore never rests on colour: the category bar chart and the Sankey label every band and have a data table, the donut adds a texture per slice and a labelled legend with percentages. Adjacent order is what the donut and any stack drawn in fill order get.

### 1.5 Event and status roles

Event: wash step 3, border step 7, dot = the fill step, ink step 11 (step 12 in light for cyan, green, lime, orange, teal and yellow, where step 11 is under 4.5:1 on its own wash or a chart surface). Status: wash 3, border 7, text 11 (12 in light for success/warning/info), bold 10–11 light / 9 dark. All held by `contrast.test.ts` (§2).

What the backend tests pin: `hue` in GET; the first read persists `hueForId(id)` (checked in the table); a re-read returns the stored value after it is changed directly in the database to a non-hash hue; a stored hue survives two concurrent first reads; PATCH sets `hue`, a label-only edit keeps it, `magenta` is 400, an empty body 400; POST with, without, and with a bad hue; the database refuses `magenta` (23514, `categories_hue_check`); the CHECK's list equals `CHART_HUES`; export → import round-trips the whole id → hue map, and a pre-0045 bundle (no `hue` key) imports with NULL and is seeded by the next read.

**How it is assigned.** `listCategories` selects `hue`; rows with NULL are seeded by one batched `UPDATE categories c SET hue = seed.hue FROM (VALUES …) seed WHERE c.id = seed.id AND c.user_id = $u AND c.hue IS NULL RETURNING id, hue`, and any row a concurrent reader got to first is read back. `AND hue IS NULL` makes the first read idempotent and means it can never overwrite a user's choice; `updated_at` is not touched. A stored value outside the vocabulary throws rather than being silently re-derived. `PATCH` takes `hue` through `COALESCE($hue, hue)`; a bad name is the existing `categorization.rule_invalid` (400). Export/import needed no code change: export is `SELECT *` minus the sensitive columns and import inserts the columns a row carries, the mechanism that made WP 10.3's `management` round-trip. Import does no application-level hue check; the column CHECK is what refuses a crafted bundle.
