# WP 10.16: The GenAI controls self-test, run inside the product against the live instance

**Request (Chris, verbatim):** "good with creating 10.16." — after the orchestrator proposed: "a controls self-test inside the product. A 'Run control checks' button on the Language model screen would exercise every control against your live instance with your own session: the approval gate refusing an unapproved shape, the level-4 cancel closing the socket, a probe that asks the model to include a number and verifies the reply is refused, an egress attempt to a non-listed host being refused, consent withdrawal turning the narrator off and revoking approvals, the inspector digest verifying, and the budget window counting. Each check writes a dated evidence row like the restore drills do, and the dashboard's backup line would show when the controls were last proven."

**Result.** Settings, Language model has a **Control checks** section: the cost stated before a press ("This sends up to 3 calls to Anthropic with your key, from this install's hourly window of 30."; for the local model "up to 3 short probes … Nothing leaves this machine"), an optional "Also prove kill switch 1", and **Run control checks** (passkey step-up). A press writes one `ops_control_checks` row (migration 0052) with all eleven checks pending and returns 202; the api runs its half (the database: approval gate, consent withdrawal, inspector digest, kill switches 1–2, narration badge) and hands the worker its half (everything that needs a model: the level-4 cancel, the numerals refusal, the reply-format refusal, egress, the hourly window, the local pin) as the `insights.control_checks` job; the screen polls and the rows tick over pending → running → pass / fail / skipped (with its reason) / reported; the table shows check, result in words, facts in words, duration; past runs are listed with their overall (Pass / Fail / Partial / Interrupted). The dashboard's backup line appends "controls proven <date>", "controls partly proven <date>", "controls check failed <date>" (a warning) or "controls never proven". `GET /narrator/control-checks` lists the last 20; one run per holder per 10 minutes (409 `narrator.control_checks_too_soon`, `Retry-After`). `just genai-selftest holder="<name>"` runs the same catalogue from the host, writes the same row and prints the same table in text (exit 0 pass / 2 partial / 1 fail). The api still has no path to a model: the preview runtime's narrators carry no probes (asserted, and sabotaged red); every model probe runs in the worker through the narration's own adapter, key, window, egress policy and reply format.

**State of the tree.** Uncommitted, on `main` at `64354ba`. Nothing staged by this WP.

**Not done by design.**

- **No live call to OpenAI, OpenRouter or Anthropic, and no call to the `ollama` container.** The hosted path is proved through the real hosted adapter over the hermetic vendor fake (`@advisor/local-model/test`), the local path over the fake Ollama server. Chris's first press is the live check (for a hosted provider it spends up to 3 calls).
- **The level-4 probe run is not an `advisor_runs` row.** Writing one would change the holder's run history (forbidden by the honesty rules). The check uses the production watcher (`watchRun`, its 1 s poll) over the production verdict (`decideContinue`) with the run's cancel flag held by the check, set 150 ms after the probe starts, and the adapter's new abort counter; the database half of level 4 (`cancel_requested_at` → the watcher's read) stays covered by `advisor-runs-routes` / `phase5-wiring`.
- **The approval-gate check holds levels 1–3 on inside its rolled-back transaction** (the holder's kind switch ships off; without this the run would be refused `kind_disabled` and the gate never reached). The real `runAdvisor` runs, with a sentinel model port that sends nothing; the facts say so.
- **"Payload approvals would be revoked" (consent check)**: withdrawal turns the narrator Off but, by WP 10.6's design, revokes nothing itself; the check proves the approvals are withdrawn on the way back — after a fresh consent, making the provider active again revokes every live approval (rolled back).
- **POST returns 202 and runs in the background** rather than holding the request for up to 5 minutes (a local probe can take minutes); the UI and the recipe read the row. A run whose api process died mid-way reads `interrupted` after 10 minutes.
- **The job is registered only where `module.insights` is on** (it is part of that module). With the module off at worker boot, the worker half reads "The worker never picked this up within 5 minutes (is the worker running, with the insights module on?)" — skipped by name, overall partial.
- **Not an HTTP operator path**: no ops route takes an operator token, so the recipe composes the run directly in a one-shot api container (KEK derivation, like `bootstrap-user`) and hands the worker its half through the job queue. Not run against a live stack here (no `docker compose run`); the script was spawned as a process against a scratch database in `narrator-control-checks-routes.test.ts`.
- The committed `wp10.6-settings-language-model-*.png` and wp10.9 dashboard screenshots predate the new section and the new line text; not regenerated (targeted screenshots only).

CREATE TABLE ops_control_checks (
  id                UUID         PRIMARY KEY,
  user_id           UUID         NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  started_at        TIMESTAMPTZ  NOT NULL,
  finished_at       TIMESTAMPTZ,
  provider          TEXT         NOT NULL
                                 CONSTRAINT ops_control_checks_provider_check
                                 CHECK (provider IN ('ollama', 'openai', 'openrouter', 'anthropic', 'off')),
  model             TEXT         CONSTRAINT ops_control_checks_model_check
                                 CHECK (model IS NULL OR length(model) BETWEEN 1 AND 200),
  results           JSONB        NOT NULL DEFAULT '[]'::jsonb
                                 CONSTRAINT ops_control_checks_results_is_array
                                 CHECK (jsonb_typeof(results) = 'array' AND jsonb_array_length(results) <= 32),
  overall           TEXT         CONSTRAINT ops_control_checks_overall_check
                                 CHECK (overall IS NULL OR overall IN ('pass', 'fail', 'partial')),
  evidence_version  TEXT         NOT NULL
                                 CONSTRAINT ops_control_checks_evidence_version_check
                                 CHECK (length(btrim(evidence_version)) BETWEEN 1 AND 64),
  created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT ops_control_checks_finished_has_overall CHECK ((finished_at IS NULL) = (overall IS NULL)),
  CONSTRAINT ops_control_checks_finished_after_started CHECK (finished_at IS NULL OR finished_at >= started_at)
);
CREATE INDEX ops_control_checks_user_started_idx ON ops_control_checks (user_id, started_at DESC);
