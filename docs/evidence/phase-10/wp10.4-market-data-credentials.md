# WP 10.4: Market-data keys through the product, and positions nobody could identify made visible

**Request (Chris, verbatim):** "similar to plaid can we add the credentials within the settings console or via the secrets path. Add this to the other defects and then dispatch"

**Result.** Settings, Market data has one card per provider (Tiingo, FRED, CoinGecko, OpenFIGI): what it is for, where its key comes from now (the operator's file, stored in this install since a date with the last four characters, not set, or for OpenFIGI "using OpenFIGI anonymously"), a masked key field, **Save with passkey** and **Remove**. A saved key is checked with the provider first through the existing adapter, sealed under the KEK in `provider_credentials` (the WP 10.1 table, widened), never returned, logged or exported, and reaches the worker within 30 s (at once when the event reaches its consumer), with no restart. A non-empty secret file still wins. OpenFIGI is now used anonymously when no key exists, and the mapper now actually reaches the security resolver, which it never did before (defect (e) below). A position the resolver cannot identify is a named row on Holdings and on its account's panel ("Could not identify this security", the institution's name and ticker, quantity, the institution's own value labelled as such, the reasons in plain words, no price, no gain), left out of allocation and performance and **named** in their excluded lists. Its movements are stored with `security_id` NULL and listed under Activity with the same marker.

**State of the tree.** Uncommitted, on `main` at `e2769e9`. Nothing staged by this WP. Migration `0043_provider_credentials_market_data.sql` is expand-only (DDL in §5).

**Not done by this WP, by design.** No live call to Tiingo, FRED, CoinGecko or OpenFIGI with a real key. The validation call runs through the real adapters over `@ctx/integrations`' `createFakeTransport` (with a fixed public DNS answer for the egress guard), which answers like the provider, like a provider refusing the key (400/401/403), and like one that is down (503). **The live check is Chris's first use.** `~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets were not read, listed, built or touched. Every database test ran against this WP's own Postgres, `docker compose -f compose.dev.yml -f /tmp/wp104/compose.override.yml -p wp104` on `127.0.0.1:5544`. The migrate test ran with `MIGRATE_TEST_DB_PREFIX=wp104`.

### The routes

| Operation id                  | Method and path                                     | Guard                    | Responses                                                                                                                                                                                        |
| ----------------------------- | --------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `getMarketDataCredentials`    | `GET /market-data/providers/{provider}/credentials` | session                  | 200, 400, 401, 503                                                                                                                                                                               |
| `putMarketDataCredentials`    | `PUT …` body `{ key }` (16–256, `[A-Za-z0-9_-]`)    | session plus **step-up** | 200; 400; 401; 403; 409 `provider_credentials.managed_by_files` / `market_data.provider_narrowed_out`; 422 `provider_credentials.rejected`; 502 `provider_credentials.provider_unavailable`; 503 |
| `deleteMarketDataCredentials` | `DELETE …`                                          | session plus **step-up** | 200, 401, 403, 503 (idempotent)                                                                                                                                                                  |

Status (`MarketDataCredentialsStatus`): `provider, purpose, source (file|stored|none), configured, anonymous, keyHint, storedAt, rotatedAt, narrowedOut`. The validation call is recorded in `market_data_runs` as a `test_fetch` (ok / refused / failed), so it spends against the same ledger as the refresh.

### Why the table rather than the events (deliverable 4)

`SecurityResolutionFailed` carries no account, quantity or value, and the log is append-only, so "has it since resolved?" needed a second lookup by identifier key. That lookup misses a resolution through a different identifier. The table is replaced per (account, provider) on every run that reported holdings for the account, so a position that resolves is simply not re-inserted, and one that still fails is rewritten with today's quantity and value (tests: "a later run that resolves the position clears its row; one that still fails rewrites it", sabotage B17). Cost: rows appear after the next investment sync, not retroactively.

## 5. Migration DDL (0043)

```sql
ALTER TABLE provider_credentials DROP CONSTRAINT provider_credentials_provider_check;
ALTER TABLE provider_credentials ADD CONSTRAINT provider_credentials_provider_check
  CHECK (provider IN ('plaid', 'tiingo', 'fred', 'coingecko', 'openfigi'));
ALTER TABLE provider_credentials ALTER COLUMN env DROP NOT NULL;
ALTER TABLE provider_credentials ADD CONSTRAINT provider_credentials_env_by_provider
  CHECK ((provider = 'plaid') = (env IS NOT NULL));

ALTER TABLE investment_transactions
  ADD COLUMN security_unresolved BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN provider_security_name TEXT,
  ADD COLUMN provider_ticker TEXT;
ALTER TABLE investment_transactions ADD CONSTRAINT investment_transactions_unresolved_has_no_security
  CHECK (NOT security_unresolved OR security_id IS NULL);
ALTER TABLE investment_transactions DROP CONSTRAINT investment_transactions_trades_name_a_security;
ALTER TABLE investment_transactions ADD CONSTRAINT investment_transactions_trades_name_a_security
  CHECK (type NOT IN ('BUY', 'SELL', 'REINVESTED_DIVIDEND') OR security_id IS NOT NULL OR security_unresolved);

CREATE TABLE unresolved_holdings (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  account_id UUID NOT NULL,
  provider TEXT NOT NULL CHECK (length(provider) > 0),
  provider_security_id TEXT, name TEXT, ticker TEXT,
  quantity NUMERIC(38,18) NOT NULL,
  institution_value_minor BIGINT,
  currency CHAR(3) NOT NULL,
  abstentions JSONB NOT NULL DEFAULT '[]'::jsonb CHECK (jsonb_typeof(abstentions) = 'array'),
  sync_run_id TEXT,
  as_of_date DATE NOT NULL,
  observed_at TIMESTAMPTZ NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX unresolved_holdings_user_account_idx ON unresolved_holdings (user_id, account_id);
-- plus COMMENTs (see the file)
```

Every row valid before is valid after: the two re-declared CHECKs are wider, the new CHECKs hold for every existing row (all are plaid with an env; `security_unresolved` defaults FALSE), and `ADD COLUMN … NOT NULL DEFAULT FALSE` is catalogue-only on Postgres 11+.

## 6. For Chris on first use

1. `git pull && just upgrade` (migration 0043; the pre-migration backup is automatic).
2. Settings, Market data: paste the CoinGecko (and Tiingo) key, **Save with passkey**. That is the live check: one cheap call with your key. A wrong key says so and stores nothing.
3. Run Sync now on the Plaid connection. The IRA's and 401(k)'s unidentifiable positions appear on Holdings as named rows with the institution's values, and their movements appear in Activity.
4. **Prices will still not refresh nightly** until (f), the refresh planner, is built. A manual test fetch works.
