# WP 10.10: The Cash Flow hub (V3 of the visual programme)

**Request (Chris, verbatim):** "Dispatch v1 and once complete continue thru v8" — after "i really like the visuals within monarch money when it comes to spend tracking and other financial health … identify strategic visual improvements to more formally mirror it." V3 is §3's third item of `docs/research/10-visual-design-notes.md`: a `/cash-flow` hub (Monarch's equivalent, §1.4).

**Result.** `/cash-flow` (nav: Money, between Transactions and Budget; also the mobile More sheet) has three tabs — **Cash flow / Income / Spending** — each with **Display by** (Cash flow: Flow = the Reports Sankey, Bars = income and expenses per period with net cash flow as a line over them; Income and Spending: Bars or Categories = the Reports category-by-month chart) and **Timeframe** (Month / Quarter / Year) with a ‹ › stepper that never passes today and a "This month/quarter/year" reset. The summary strip shows Income · Expenses · Net cash flow · Savings rate, signed and sign-coloured, "so far" on the current period; the rate is withheld with a sentence when the period is incomplete, has no income, has no data or has not started. Beneath it the comparison row switches between _vs last period_, _vs 12-period average_ and _vs same period last year_, each a sentence in money with a direction word and both amounts, never a bare percentage; the current period's counterparts are read **through the same point**; a counterpart with no ledger row is withheld and says what is missing. Breakdowns by category, by category group and by merchant are Monarch's horizontal bar rows (two-letter avatar tinted by the row's hue, bar = share of the side's total, amount, share and count), sorted, the tail past twelve folded into "Other (n …)" without losing a cent, each row a link to `/transactions` with the row's own filter. The whole view is URL state. Every figure is served by a new `GET /reports/cash-flow`, which **is** `GET /reports/spending` / `/reports/income` over each figure's window — asserted against both routes. Building it found three real things (§0).

**State of the tree.** Uncommitted, on `main` (dispatched at `27c0a84`; HEAD is now `042cffb`, the orchestrator's execution-log commits, which touch none of these files). Nothing staged. No migration. No new runtime or dev dependency; no lockfile change. The 16 PNGs under `docs/evidence/phase-10` that are not this WP's (`wp10.3-*` modified, `wp3.11-*` untracked) were not touched; this WP's twelve screenshots were written by a targeted run only (`-g "WP 10.10 evidence"`). The profiling scaffold used in §0 (`apps/api/test/db/wp1010-scratch-profile.test.ts`) was deleted; it was never a test.

**Not done by design.**

- **The current-year timeframe is measured, not asserted, against the 200 ms budget.** A complete year on the dense corpus is p95 **91–99 ms** across six runs (asserted). The current year reads all 50,040 rows (the selected year plus the twelve before it, every counterpart cut at today) and sits **at** the budget: p95 195.3 / 200.8 / 197.9 / 207.6 / 209.6 ms, p50 ~150–175, over six quiet runs. Postgres summing the 50k rows on one backend is ~85 ms of it (in-process profile); two shards on two connections made it worse (p50 184 / p95 216, reverted). Meeting it reliably needs a maintained monthly aggregate — a schema change outside this package (ORCHESTRATOR line, §6).
- **No user-level base currency exists** (checked: the only `base_currency` is per net-worth snapshot). The hub follows the pace's rule: one currency, the one with the most rows; the others are named, "Activity in EUR is not included (never converted)", the wording the pace uses.
- **Merchant rows have no drill-through for "No merchant"**, and "Other" has none: no `GET /transactions` filter reaches exactly them, so they are not links rather than links to a superset.
- **The Sankey shows spending flows only** (income → category → merchant), as it always has: "Flow = the existing Sankey". The income side is on the Bars display and the Income tab.
- **`hueForId(merchantKey)` uses the merchant's id** as the key: `merchants` is unique on `(user_id, normalized_key)`, so id and normalised key are one-to-one, and the web can compute the same hue from the id the row already carries.
- README has no screens list (its only screen mention is the install walk-through reaching the dashboard); nothing to update there.

## 0. What building it found

- **(a) The first route was 2–3× over budget.** Reading every row of a twelve-period window: year p95 **357 ms**, current year **559 ms** (dense). Profiled in-process: drizzle's builder mapping ~70 of ~195 ms for 31k rows, then repeated `computeActuals` passes. Fixed in four steps, each measured: (1) `@ctx/ledger listAggregateRowsInWindow` as one plain statement (195 → ~120 ms for 31k rows; also cuts the pace's dense p95 from ~100 to **68.7 ms**); (2) `windowReader` computes each month once per refund-resolution context; (3) the hub reads its window **summed** — `listAggregateSumsInWindow` groups rows `computeActuals` treats identically (account, segment of month, both category tiers, merchant, transfer flag, link presence, exclusion; `count` kept as a weight) and `listRefundLinkedRowsInWindow` returns refunds and the purchases they name one by one; the two reads partition the window exactly (ledger-db test); (4) that statement first took 68 ms for 72 groups — its `ORDER BY` turned a hash aggregate into a sort of all 25k rows and `date_trunc` went through `timestamptz` per row: dropped / replaced by integer date arithmetic (34 ms), and the current period's cut dates became a hashed `VALUES` join on the month instead of a CASE branch per cut. Final numbers in §2.
- **(b) The shared Sankey's bands could never pass 2.4.11.** On the hub the Sankey is on screen by default (Reports hides it behind a tab, which is why the Tab walk never reached it there). The sweep found: a level band, drawn as a thick stroke, has a zero-height geometry box — "outside the viewport" (the same artefact `budget.spec.ts` worked around with `click({ force: true })`); redrawn as a **filled ribbon** whose box is the band, the next run found the bands **overlap by nature**, so a focused one is always partly covered by a neighbour. Fixed: bands are pointer targets (`aria-hidden`, still clickable), and the keyboard's and screen reader's way to the same drill-through is the chart's own table, now one link per flow ("Groceries, view transactions"). This also removed dozens of tab stops, and the names stopped being node ids ("Flow from income to category:cat_rent"). Reports' test and `budget.spec.ts` updated (no `force` needed any more).
- **(c) Merchant drill-through never landed filtered.** `transactionsSearchSchema` had no `merchantIds` (the open item `docs/evidence/phase-2/wp2.9-budget-ui.md` recorded), so a Sankey merchant band landed on the whole category. Added `merchantIds` (and `uncategorized` on the drill object) end to end; `/transactions` shows "Merchant: Corner Grocery — Remove merchant filter".
- Also: the categories chart and the Sankey labelled categories the categories list had not loaded as "Unknown category" and coloured them by hash while the breakdown beside them used the persisted hue; the hub now hands its charts the server's own labels and hues. Two lint findings (a `role` prop on a key glyph; an `import()` type) fixed.

**The bars chart, by the dataviz method.** The job is magnitude over time of two sides that belong together, so paired columns per period on **one** money axis, income then expenses (position carries identity as well as hue), and net cash flow as a 2 px line with 8 px dots ringed 2 px in the surface, on the same axis (it is money; never a second scale). Columns ≤ 24 px, a 2 px gap between the pair, 4 px rounded data-end, square at the baseline; solid hairline grid; compact tabular y ticks; the zero line in the axis role and the negative-area wash below it; the selected period on a quiet band, bold on the axis and `aria-pressed`. Every period is a button that selects it and shows the readout on hover or focus (WCAG 1.4.13 via `useChartTooltipRules`). A period with no ledger row draws nothing, never a zero column, and says "No data" in the readout and the table. A legend for the three marks (none for a single side); **View as table** carries every value; the `aria-label` names the range and the selected period's figures ("March 2026: income $5,200.00, expenses $1,512.50, net $3,687.50 so far."). Nothing animates. `validate_palette.js --pairs all` on `--chart-income, --chart-expenses, --chart-line`: light `#0f8a68,#d2452f,#2563eb` on `#fdfdfc` **ALL PASS** (worst CVD ΔE 9.9 deutan, normal-vision 25.2); dark `#1ba277,#e8604a,#3987e5` on `#191918` **ALL PASS** (8.8, 20.5). `contrast.test.ts` measures every mark role at 3:1 and the tick text at 4.5:1 on every chart surface **and on the selected band**, both themes.

**Every figure is Reports over a window.** For a window `[from, to]`: rows by Reports' filters; cells by `categoryMonthCellsOf` (the same `monthActualsOf` → `computeActuals`: transfers out on both legs, refunds netted into the purchase's category, holder-excluded rows and off-budget accounts dropped, pending **counted**, as Reports counts them); sides by `spendingRowsOf` / `incomeRowsOf` unchanged. Expenses = −Σ spending cells, income = Σ income cells, net = income − expenses. Each period is computed over **its own window's rows** (`categoryOfPurchase` spans exactly them), because that is what the report for that window does. The summed read changes how many rows arrive, not what they add to: `apps/api/test/cash-flow.test.ts` asserts `windowReader` over summed rows equals `cellsOfWindow` over the raw rows for 100+ windows of a generated ledger with cross-month refunds, transfers, exclusions, an off-budget account and a second currency, and the route tests compare with `GET /reports/spending` and `/income` directly.

## 6. Hand-off
