# WP 10.1: Plaid credentials through the product

**Request (Chris, verbatim):** "i want to make it so that i can add my plaid credentials via the add connections menu and have them securely stored as tied to the setup."

**Result.** A holder opens Accounts, Add connection, the Plaid tab, pastes their Plaid client id and secret, chooses sandbox, saves with a passkey, and the Link card appears in the same document. The keys are checked with Plaid before they are stored, sealed with the same key that protects Plaid access tokens, never returned, never logged, never exported. The operator's secret files still win when they are non-empty. No restart, no file, no `PLAID_ENABLED` change for the connector (the proxy's CSP switch is unchanged and still needed for Link's script).

**State of the tree.** Uncommitted, on `main` at `c40b51d`. Migration `0041_provider_credentials.sql` is expand-only (one `CREATE TABLE`, one unique index, comments; it references only `users`).

**Not done by this WP, by design.** No live Plaid call with real credentials was made. The validation call is exercised against the hermetic `FakePlaidApi` (`@connector/plaid/test`) and a scripted subclass that rejects like Plaid does. **The live sandbox check is Chris's first use.** `~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets were not read, listed, built or touched.

### The AAD

`personalfi/v1 | provider_credentials | client_id_sealed or secret_sealed | <user_id>.<provider> | <key version>`. The record scope of the DEK is `provider_credentials:<user_id>.<provider>`. Removing the credentials retires that DEK (`destroyRecordKey`, after the delete commits, because retiring a key is not transactional and a rolled-back delete with a retired key would strand the row), so a copy in an earlier backup cannot be opened either.

### The routes (exact operations, for `just openapi`)

All under tag `connections`; emitted and checked with a throwaway copy of `emit-openapi` writing to `/tmp` (the repo's `packages/contracts` was not touched).

| Operation id             | Method and path                                   | Guard                    | Responses                              | Notes                                                                                                                                                                                                               |
| ------------------------ | ------------------------------------------------- | ------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getPlaidCredentials`    | `GET /connections/providers/plaid/credentials`    | session                  | 200, 401, 503                          | `PlaidCredentialsStatus`: `configured`, `source` (`files`, `stored`, `none`), `env`, `clientIdHint`, `rotatedAt`, `productionAllowed`.                                                                              |
| `putPlaidCredentials`    | `PUT /connections/providers/plaid/credentials`    | session plus **step-up** | 200, 400, 401, 403, 409, 422, 502, 503 | Body `{ clientId, secret, env }`. 409 `provider_credentials.managed_by_files`; 403 `provider_credentials.production_refused`; 422 `provider_credentials.rejected`; 502 `provider_credentials.provider_unavailable`. |

`productionAllowed` is one field beyond the brief's GET shape, added because the UI must offer production "only when the api says it is allowed".

### Decisions and deviations, stated

1. **Validation call.** `/institutions/get` is not on the adapter's eleven-method allow-list (`PlaidApiLike`; adding a method is a deliberate edit in `packages/connectors/plaid`, which is not this WP's, D16). The cheapest authenticated call that is on it is `/link/token/create`: free (Plaid bills when an Item is created), works in both environments, and is the call the product makes next anyway. A bad key or wrong environment surfaces as `INVALID_API_KEYS`, `INVALID_CLIENT_ID` or `UNAUTHORIZED_ENVIRONMENT` (a `CONFIG_ERROR`). If Chris wants `/institutions/get`, that is a one-method addition to `api.ts`, `fake.ts` and the route.
2. **Per-holder registry resolution, not a mutable global registration.** A deployment-wide registry that one holder's request mutates would be a cross-holder bug in a deployment that ever has two holders, so Plaid for stored credentials is resolved per `userId` and the synchronous `get/has/manifests` surface sees only static registrations. The cost is that the call sites that need Plaid (orchestrator, `connections.ts`, `plaid.ts`) are `await registry.connectorFor(provider, userId)`.
3. **The audit event is written after the credential commits**, through `recordSecurityEvent(pool, ...)`, not in the same transaction (that function takes the pool). The domain event, which is in the transaction, still records the change. Recorded as a residual in the threat model.
4. **`SecurityEventKind` cast.** The three kinds `provider_credentials.set | .rotated | .removed` are cast into `SecurityEventKind` in the route, because the union lives in `packages/contexts/identity` (not this WP's). The column is free text, so it works; see Wiring.
5. **The export test lives in `apps/api`.** The brief put 'a stored credential never appears in an export bundle' in the connections test file, but the exporter is in `apps/api` and `@ctx/connections` may not import it. It is in `apps/api/test/db/provider-credentials-routes.test.ts` under the exact name; the connections test carries the at-rest and scoping claims.
6. **Change and Remove are in the dialog**, under the Link card, not in Settings, Security. That screen is about how you sign in (passkeys, the authenticator code, sessions); a bank-linking key tucked there would be a second place to learn, and the dialog is where the holder meets Plaid and where a "why can't I sync" question starts.
7. **Test seams added to `buildApp`** (`plaidApiFactory`, `logStream`), both optional and absent in production, and to the api test harness (`appBuildsRegistry`, `plaidApiFactory`, `logStream`, `env`, and `config` on the returned harness; all additive).
8. **Test order.** The tests were written after the implementation in this WP, so the "red" evidence is sabotage-based (section 3), not a red run before the code. Each control below was sabotaged once and observed red, then restored.

## 5. For Chris on first use

1. `git pull && just upgrade` in `~/personalfi-prod` (migration 0041; expand-only; the pre-migration backup is automatic).
2. In `.env`, `PLAID_ENABLED=true` is already set on production; keep it (it is the proxy's switch for Plaid Link's script).
3. Accounts, Add connection, Plaid, "Set up Plaid": your Plaid **sandbox** client id and secret, environment Sandbox, Save and continue, touch the passkey. That is the live check: it makes one `/link/token/create` call to Plaid's sandbox with your keys. A wrong key says so in words and stores nothing.
4. Then "Connect with Plaid" and link a sandbox bank (`user_good` / `pass_good`).
5. Do not put real data through `production` until `PLAID_ALLOW_PRODUCTION=true` is deliberately set in `.env` and the stack restarted.
