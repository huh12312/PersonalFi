# WP 12.1: Caddy from source on a patched Go

**Request.** `docs/research/13-docker-hub-publishing.md` §2 point 2 and §5 item 1. The proxy image wrapped upstream `caddy:2-alpine` by digest (v2.11.6, `sha256:d44355d3…`). Its `/usr/bin/caddy` was compiled by upstream with Go 1.26.8, `golang.org/x/net` 0.59.0 and `go-jose/v4` 4.1.5, and carried six HIGH findings snoozed in `.trivyignore` to 2026-11-07 (CVE-2026-78667, -78669, -97031, -111943, -56857 in the Go standard library and x/net; CVE-2026-116587 in go-jose). No upstream build cleared them: the 2026-10-22 rebuild of 2.11.7 still shipped Go 1.26.8, and Caddy 2.11.7's own `go.mod` still requires x/net 0.59.0 and go-jose 4.1.5. Docker Hub shows its scanner's findings on the repository page, so a published image has to scan clean for real.

**Result.**

1. **`docker/caddy.Dockerfile` compiles Caddy.** A `caddy-build` stage runs on the build platform from `golang:1.26.10-alpine3.24` by digest. It installs xcaddy v0.4.7, pinned by version and module checksum, and cross-compiles Caddy **v2.11.6** for `TARGETOS`/`TARGETARCH`, with `golang.org/x/net` raised to **v0.60.0** and `go-jose/v4` to **v4.1.6**. The flags are `CGO_ENABLED=0`, `-trimpath`, upstream's tags and an empty build ID. There are no plugins.
2. **The runtime stage is upstream's own base, alpine 3.23.6 by digest,** plus the two packages upstream adds that this proxy uses (`ca-certificates`, `mailcap`). It keeps the same user (10003), the same directories and modes, the same XDG environment, working directory and command, and the same web-build copy. The binary has no file capability and libcap never enters the image.
3. **Three build-time controls, each sabotaged red (§3):**
   - the xcaddy checksum;
   - the linked module versions, read back from the binary's build info;
   - the module-list pin: `caddy list-modules` must equal the new `docker/caddy-modules.txt`.
4. **CI's exact scan, without `--ignorefile`: 6 → 0** in `usr/bin/caddy`, and 0 in the alpine layer, on amd64 and on arm64 (§2.4).
5. **The six snoozes are retired.** `.trivyignore` keeps its history, with a closing paragraph dated 2026-11-01. The trivy-fs expiry tripwire passes over it (§2.9).
6. **The image went from 181 MB to 98 MB** (§2.5). The old build carried upstream's 52 MB binary twice: `setcap -r` rewrote it into a new layer.
7. **Renovate.** A `customManagers` regex reads the four `# renovate: datasource=go` ARGs. A `packageRules` entry groups the Go image, Caddy, xcaddy and the two floors into one PR ("proxy: Caddy from source", never auto-merged). A second rule keeps the Go image on the 1.26 line (§1.6).
8. **Docs.**
   - RUNBOOK: a new "The proxy image: Caddy from source" under Upgrade (the pins, how a bump lands, what to do when trivy finds something first), and the "operation not permitted" troubleshooting entry rewritten.
   - Release notes: `## v0.10.0 (in preparation)` with this item.
   - 13 §7 row 12.1 points here.

**State of the tree.** Uncommitted, on `main` at `ce61bcd` (HEAD at the start; unchanged). Nothing is staged. The 16 phase-10 PNGs were not touched. Changed: `docker/caddy.Dockerfile`, `.trivyignore`, `renovate.json`, `RUNBOOK.md`, `docs/RELEASE-NOTES.md`, `docs/research/13-docker-hub-publishing.md` (one row). New: `docker/caddy-modules.txt` and this file.

**Not run, by instruction:** `bash scripts/upgrade-test/run.sh --path direct --ci`. It takes too long, and the dispatch excluded it. The upgrade path is unaffected in kind: `just upgrade` builds the proxy image as before. It now also compiles Caddy.

### 1.2 xcaddy: `go install …@version`, with the module sum verified

`go install github.com/caddyserver/xcaddy/cmd/xcaddy@${XCADDY_VERSION}` runs under `GOFLAGS=-mod=mod` and `GOTOOLCHAIN=local`. Go verifies the module zip against `sum.golang.org` on the way in. The Dockerfile then reads the installed binary's build info (`go version -m`) and refuses unless its main-module line is exactly `${XCADDY_VERSION} ${XCADDY_SUM}`.

I chose this over downloading a release tarball by checksum for three reasons:

- The builder runs on the build platform, so a tarball needs a per-architecture checksum table.
- The tarball's host (GitHub releases) is one more network dependency. The Go module proxy is already needed for Caddy's own modules.
- The `h1:` sum is the module's content hash in a public transparency log.

The pinned sum means a changed `GOPROXY`/`GOSUMDB` cannot substitute the tool. A Renovate bump of `XCADDY_VERSION` alone fails the build by name until the sum is updated in the same PR (sabotage S4 shows the message). That one manual line per xcaddy release is deliberate.

### 1.3 The module floors: `--with`, not `--replace`

xcaddy's `--with module@version` runs `go get module@version caddy@${CADDY_VERSION}` and adds a blank import to the generated `main.go`.

- **What `--with` points at.** `golang.org/x/net` has no package at its root, so the floor is given as `--with golang.org/x/net/http2@${XNET_VERSION}`. The go-jose floor is `--with github.com/go-jose/go-jose/v4@${GOJOSE_VERSION}`. Both packages are ones Caddy already links (`http2` via `net/http`'s bundle and quic-go; go-jose via smallstep). The import adds no Caddy module, and the module list proves it (§2.3).
- **Why not `--replace`.** `--replace` writes a `go.mod` `replace`, which pins the version even if a later Caddy needs a newer one: a silent downgrade. A `go get` floor instead takes part in minimum version selection. A later Caddy that requires more fails the `go get` loudly.
- **The build log shows the floors applied:** `go: upgraded golang.org/x/net v0.59.0 => v0.60.0` and `go: upgraded github.com/go-jose/go-jose/v4 v4.1.5 => v4.1.6`.

### 1.4 The runtime stage: alpine, not `caddy:2-alpine`

The dispatch asked that the runtime stage "stays what it is … with the built binary dropped in", and that the image's size not regress. Dropping a binary on top of `caddy:2-alpine` cannot meet the second condition: upstream's 52 MB binary would stay in a lower layer, adding about 52 MB. Renovate would also keep proposing digest bumps for a Caddy the image no longer runs.

So the runtime is the base that `caddy:2-alpine` itself starts from, alpine 3.23.6 by digest. To it I added what upstream's Dockerfile adds and this proxy uses. I compared the result with the old image file by file:

### 1.6 Renovate

`renovate.json`:

- **`customManagers`.** One regex manager on `docker/caddy.Dockerfile` reads `# renovate: datasource=go depName=<module>` followed by `ARG <NAME>_VERSION=<value>`. I checked the regex against the file (Python, same pattern): it extracts exactly the four values, Caddy `v2.11.6`, xcaddy `v0.4.7`, x/net `v0.60.0` and go-jose `v4.1.6`. `XCADDY_SUM` is deliberately not matched.
- **The builder image** (`ARG GO_IMAGE=golang:…@sha256:…`, used in a `FROM`) is picked up by the Dockerfile manager, as the existing `NODE_IMAGE`/`CADDY_IMAGE` pins were. It falls under the existing docker digest-pinning rule (`pinDigests: true`). The Go-module ARGs have no digest. Their content pin is the module sum Go verifies, plus xcaddy's explicit `h1:` sum.
- **Group rule (new).** It matches `docker/caddy.Dockerfile` and `golang`, `github.com/caddyserver/caddy/v2`, `github.com/caddyserver/xcaddy`, `golang.org/x/net` and `github.com/go-jose/go-jose/v4`. It sets `groupName: "proxy: Caddy from source"` and `automerge: false`. It sits after the "all non-major dependencies" rule, so it takes these packages out of that group.
- **Go line rule (new).** `golang` gets `allowedVersions: /^1\.26\./`. Moving to 1.27 is a decision taken with a Caddy release built on it.

**What Renovate will propose.** Its schedule is Monday 00:00–06:00 New York, and the seven-day `minimumReleaseAge` applies. On today's registry state:

- **In the proxy group:**
  - Caddy `v2.11.6 → v2.11.7`.
  - x/net `v0.60.0 → v0.61.0`, and `v0.62.0` from 2026-11-03.
  - go-jose `v4.1.6 → v4.1.7` from 2026-11-06.
  - No golang bump: 1.26.10 is the newest 1.26 patch.
  - No xcaddy bump: v0.4.7 is the newest.
- **In the existing non-major group:** the alpine pin moves to the newest tag in the alpine series, digest-pinned. That is 3.23.7, or 3.24.3 if Renovate's docker versioning takes the minor; it does not split minor from patch here. I have not run Renovate itself. These are predictions from the config and the registries, not observations.

### 2.6 Nothing else regressed

- **Headers, served by the image itself.** Both images were booted with compose's hardening: `--cap-drop ALL --security-opt no-new-privileges:true --read-only --user 10003:10003`, compose's two tmpfs mounts, a volume at `/data`, the real `docker/Caddyfile` mounted read-only, and `--network none`. For each I fetched `http://127.0.0.1:8080/` from inside the container. The two header sets are identical: `Content-Security-Policy` (the full policy string, byte-equal), `Cross-Origin-Embedder-Policy: require-corp`, `-Opener-Policy`, `-Resource-Policy`, `Permissions-Policy`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`.
- **Content types (mailcap).** The `Content-Type` of one file of each extension in `/srv/web` is identical across the two images: `.css`, `.txt`, `.md`, `.woff2`, `.svg`, `.png`, `.html`, `.webmanifest`, `.js`.
- **Process state.** Both run as uid 10003 with `CapPrm`, `CapEff` and `CapBnd` all `0000000000000000` and `NoNewPrivs: 1`. Because the after binary runs under `no-new-privileges` with an empty capability set, it demonstrably carries no file capability.
- **Errors in the boot logs.** Each logged one error line, the same one: `pki.ca.local … failed to install root certificate` (a read-only container cannot write the host trust store). It is expected and pre-existing.
- **`apps/web/e2e/csp.spec.ts`** (the `csp` project) is the spec that re-derives the CSP from `docker/Caddyfile`. It serves the bundle from `e2e/csp-static-server.mjs`, not from the image. `docker/Caddyfile` is unchanged by this package, so the spec's input is unchanged. Its run is in §2.10.
- **`csp-plaid.spec.ts`** runs Caddy from its own hard-coded `caddy:2-alpine@sha256:5f5c8640…`, an older upstream digest than even the previous pin. It does not exercise this image (§6).
- **`scripts/upgrade-test/dockerfile-pin-policy.test.ts`** (every `FROM` digest-pinned, including `--platform=$BUILDPLATFORM ${GO_IMAGE}`; no apk build pins) and **`scripts/caddy-headers.test.ts`** (G-14, which reads `docker/caddy.Dockerfile`): 2 files, 22 tests passed.
- **`bash scripts/compose-hardening-check.sh --self-test` and `bash scripts/compose-hardening-check.sh`:** PASS. 32 rules fire on the hostile fixture, the layered override is caught, and `compose.yml` has 11 services with 0 violations. `compose.yml` is not changed by this package.

## 6. For the orchestrator

- **Choices made:**
  - **The runtime base.** It is alpine 3.23.6, not `caddy:2-alpine` with the binary dropped on top (§1.4). That is the only way the size could not regress, and it went 181 → 98 MB. Every property the dispatch listed is unchanged (user, directories, environment, command, no capability, the same Caddyfile in use, the web copy). Two deliberate differences: `EXPOSE` now names 8080/8443, and the image carries `docker/Caddyfile` instead of upstream's unusable welcome config.
  - **`web-build` runs on the build platform** (`FROM --platform=$BUILDPLATFORM`). The bundle is architecture-independent, so the arm64 image no longer runs pnpm and vite under QEMU in `release.yml`. CI's single-arch build is unaffected.
  - **Caddy stays at v2.11.6.** Renovate's first PR in the new group will propose v2.11.7.
  - **Go 1.26.10 is inside the seven-day release age** the repository applies to npm (published 2026-10-27). No older Go fixes the x509 finding.
- **Production's next `just upgrade` compiles Caddy.** That build reaches `proxy.golang.org` and `sum.golang.org` from the production host, a new egress for the build, beside Docker Hub, the alpine CDN and npm. It adds about two minutes to a cold build. The release note says so. If the production host restricts egress at build time, it needs those two hosts.
- **Docker Scout and the unfixed go-jose/v3 HIGH.** Under the repository's policy (`--ignore-unfixed`, 06 §5.5) the image is clean, and no finding is suppressed. Docker Scout, however, typically shows unfixed findings too, so the Hub page may show one HIGH (CVE-2026-116587 in `go-jose/v3` v3.0.5, which smallstep pulls in and which has no fixed v3 release). It may also show the MEDIUM/UNKNOWN ones in §2.4. For 12.2/12.5: decide whether that is acceptable, or watch for a smallstep release that drops v3. A chi floor at v5.4.0 would clear the MEDIUM. Neither is in this package's HIGH/CRITICAL scope.
- **`csp-plaid.spec.ts` pins its own stale Caddy.** It hard-codes `caddy:2-alpine@sha256:5f5c8640…` while its header says it uses "the same pinned image `docker/caddy.Dockerfile` ships". That was already untrue before this package (the Dockerfile pinned `d44355d3…`), and is now further from true. Pointing it at a locally built proxy image, or at the new pins, is a small follow-up. I did not change it: it is outside this package's files and runs a container from a pull. `docker/Caddyfile` is unchanged, and the image's headers were compared directly (§2.6).
- **`just hardening-check`** fails only on C-16 (the dev checkout's secret ownership, §2.10). Chris runs `sudo just harden-secrets`.
- **Commit hygiene.** Commit `docker/caddy-modules.txt` (new) with `docker/caddy.Dockerfile`: the build bind-mounts it, and fails without it. Nothing is staged. Check `git status` for staged entries before an explicit-path commit.
