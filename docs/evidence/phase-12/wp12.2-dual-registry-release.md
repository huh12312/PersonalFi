### 1.3 Choices

- **The owner is written out, `huh12312`, not computed.** `scripts/verify-release.sh` writes it out, as do the Hub README and SECURITY.md. A fork pushing a tag would fail at the GHCR push rather than publish under another name.
- **`verify` is anonymous on both registries.** That is how a community install and `verify-release.sh` read them. A package that is not public (GHCR may create its three as private, §6) fails verify, before any release exists. Anonymous use also keeps `DOCKER_PAT` out of a third job. The cost is Docker Hub's anonymous rate limit. The job makes about two manifest reads per Hub image (the tag resolution, and cosign's signature lookup), and a `429` fails the job. "Re-run failed jobs" re-runs only `verify` and what follows it, with no rebuild and no second approval.
- **The identity.** `verify` builds `https://github.com/huh12312/PersonalFi/.github/workflows/release.yml@refs/tags/v${version}` exactly as `verify-release.sh` builds it, and passes it as an exact `--certificate-identity`, as the script does. That is the anchored form of the `^https://github.com/huh12312/PersonalFi/\.github/workflows/release\.yml@refs/tags/v…` regexp, tied to this one version. It adds `--certificate-github-workflow-sha "$GITHUB_SHA"`, the script's `--commit` check.
- **`hub-readme` runs after `verify`, beside `github-release`, not before it.** A description that fails to update (the token's scope, §6) should not hold back a verified release. A release that fails verification should not get a refreshed Hub page.
- **No `labels:` from metadata-action.** Its defaults would replace each Dockerfile's per-image `org.opencontainers.image.title`/`description` with the repository's. The Dockerfiles' `org.opencontainers.image.source` is stale (`https://github.com/chris/personalfi`), which is a follow-up (§6).

## 3. The two attestation paths, and the two signature paths

`actions/attest-build-provenance` v4.2.2 is a composite action over `actions/attest` v4.2.1 (`508db95d…`). Its `createAttestation` (`src/attest.ts` at that commit, read with `gh api`) does two things in order:

1. **It signs the provenance and writes it to GitHub's attestation store** (`attest()` from `@actions/attest`).
2. **Only then, with `push-to-registry`, it calls `@sigstore/oci`'s `attachArtifactToImage`.** That pushes the bundle as an OCI 1.1 referrer of the image digest. If the registry returns no `OCI-Subject` header, or does not answer the referrers ping, it maintains a referrers index under the `sha256-<digest>` tag instead (`packages/oci/src/image.ts`, the referrers tag schema).

The subject name is `docker.io/masterhuh/personalfi-<image>`. The actions/attest README says: "When pushing to Docker Hub, please use 'docker.io' as the registry portion of the image name". Storage records are skipped either way: `repoOwnerIsOrg` is false for a personal account.

**The first real run takes one of two paths. This evidence cannot say which**, because the workflow cannot run before a tag.

| Path                                                                                                     | What the run shows                                                                                                                                                                                                                                                                                                                                | What holds                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Docker Hub accepts the referrer** (through the referrers API or the `sha256-<digest>` tag fallback) | "attest provenance (Docker Hub)" green. No warning                                                                                                                                                                                                                                                                                                | Attestations for the digest in GitHub's store under both subject names, and a referrer on each registry. A third tag-like entry `sha256-<digest>` may appear in the Hub tag list if the fallback was used                                                                                                                                                 |
| **B. Docker Hub refuses it**                                                                             | The Hub attest step red but `continue-on-error`. The job stays green with an annotation: `docker.io attestation: the provenance attestation for docker.io/masterhuh/personalfi-<image> was not pushed to docker.io as a referrer … The GitHub-store attestation for the same digest stands; the verify job checks it with gh attestation verify.` | The GitHub-store attestation, written in step 1 before the push that failed. `gh attestation verify oci://docker.io/masterhuh/…@<digest>` looks attestations up **by digest** in GitHub's store whatever the registry, and finds them: the GHCR attestation alone (same digest) would satisfy it. A Hub user without `gh` loses only the in-registry copy |

**What `continue-on-error` cannot tell apart.** If the Hub step failed earlier, in signing or in the GitHub-store write rather than at the push, the warning reads the same. Nothing is lost then either: the GHCR attestation, which is not soft, covers the same digest, and `verify` hard-checks `gh attestation verify` on the Hub reference. The warning names the registry so the first run's log says which path happened. **12.5 should record which.**

**cosign has the same two paths, but is not soft.** cosign-installer v4.1.2 installs cosign v3.0.6, whose `sign` defaults to `--new-bundle-format=true`. That stores the signature as a Sigstore bundle attached as an OCI referrer, with go-containerregistry's tag-schema fallback where the referrers API is missing. A refusal by Docker Hub fails the publish job: an unsigned Hub copy must not be published as verified. `verify` uses the same cosign, so both sides read the same format.

## 4. Docker Scout on the public page

WP 12.1 measured the proxy image with trivy at every severity, including unfixed findings (`wp12.1-caddy-from-source.md` §2.4). This package builds no image and had no network for a re-scan, so the numbers are 12.1's. `usr/bin/caddy` showed 7 findings (HIGH 1, MEDIUM 3, UNKNOWN 3), and the alpine layer 0:

- **HIGH, CVE-2026-116587 in `go-jose/v3` v3.0.5, status `affected`.** No v3 release fixes it; smallstep pulls v3 into Caddy.
- **MEDIUM in `go-chi/chi/v5` v5.3.2, fixed in 5.4.0.**
- UNKNOWN: `x/net` v0.60.0 twice (fixed in 0.62.0, which Renovate proposes once it is seven days old) and `x/crypto` openpgp (no fix).

Under the repository's policy (`--ignore-unfixed`, HIGH/CRITICAL, 06 §5.5) the image is clean with nothing suppressed, and the release gate scans it that way.

**What the Hub page will show.** Docker Scout, where its analysis is on for a repository, lists findings per tag at every severity and does not hide unfixed ones. So `masterhuh/personalfi-proxy:0.10.0` would most likely show **1 HIGH with no fix available**, plus one or more MEDIUMs, chi among them. Scout's advisory database is not trivy's, so the exact counts may differ. Whether Scout analysis is on for a new repository under a personal namespace is an account setting (Docker Hub repository settings → Docker Scout image analysis). It cannot be read from here: verify on the first push. The api and backup images were not scanned at every severity in this package.

**Recommendation on chi (not implemented): raise the floor in 12.5, before the first tag.**

- chi v5.4.0 was published 2026-10-12, 20 days ago (`gh api repos/go-chi/chi/releases`). It is past the seven-day age the repository applies (D14), and v5.5.0 (2026-10-14) is also mature.
- It is a minor release on v5, so it is semver-compatible.
- It lands the way 12.1's floors did: a fourth `# renovate: datasource=go` ARG and `--with github.com/go-chi/chi/v5@v5.4.0` in `docker/caddy.Dockerfile`, a line in the buildinfo check, and the module in the Renovate group. 12.1's three build-time controls (buildinfo, module list, trivy) catch a wrong pin.
- The cost is one proxy build and a trivy run at every severity, before and after.
- The first public page would then carry only the go-jose/v3 HIGH, which has no fix. That one is a documented "no fix exists" (SECURITY.md is the place to say so), not something a raised floor can clear.

## 6. For the orchestrator

- **`DOCKER_PAT` is not set.** The repository has no secrets at all today (§2.5). A tag pushed before Chris runs `gh secret set DOCKER_PAT -R huh12312/PersonalFi` would fail at "log in to Docker Hub", after the approval and before anything is pushed. Nothing would be published.
- **The token's scope.** `peter-evans/dockerhub-description` documents that it needs a token with **read/write/delete** scope. A Read & Write token (often what a push-only PAT is) publishes and verifies, and fails only the `hub-readme` job. The RUNBOOK says so.
- **GHCR visibility on the first push.** If GHCR creates the three packages as private, `verify`, which is anonymous on purpose, fails on the GHCR references. Chris sets each package public and uses "Re-run failed jobs" (RUNBOOK "Cutting a release"). Docker Hub creates public repositories on first push (13 §9).
- **A risk for 12.3/12.5: cosign versions differ between signing and the install side.** `release.yml` signs with cosign v3.0.6 (cosign-installer v4.1.2's default). `scripts/verify-release.sh` runs `ghcr.io/sigstore/cosign/cosign:v2.6.1` when cosign is not on the PATH. Read offline from both images' `--help` (the v2.6.1 and v3.0.2 images were already local):
  - v3's `sign` and `verify` default to `--new-bundle-format=true`;
  - v2.6.1's `verify` defaults to `--new-bundle-format=false`.

  So the install-side verifier, run through its pinned container, may report "no signatures found" for a correctly signed v0.10.0. This could not be demonstrated here: there is no local registry image, and no network to pull one. `verify` in this workflow does not catch it, because it uses v3 on both sides. **12.3 should move `COSIGN_IMAGE` to a v3.0.x digest, or pass `--new-bundle-format`, before 12.5's tag,** and 12.5's clean-host check proves it.

- **Stale `org.opencontainers.image.source` label.** All three Dockerfiles say `https://github.com/chris/personalfi`. It is outside this package's files, and changing it changes images. It belongs with 12.3's naming work. metadata-action's `labels:` output could replace it, but it would also overwrite each image's title and description (§1.3).
- **Tag immutability: D32 and 13 §2.5 disagree.** D32 says "version and minor-line tags immutable". 13 §2.5 says `latest` and the minor-line tag (`0.10`) "stay movable by design". The workflow pushes `X.Y` on every release, so a Hub rule that made `X.Y` immutable would fail the second `0.10.x` publish. When Chris turns on immutability (a Hub repository setting, not in this package), the rule should cover `X.Y.Z` and `sha-*` only. 12.5's step.
- **`gh` in `verify`.** It uses the runner's preinstalled `gh` with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (`attestations: read`).
- **Commit hygiene.** Commit `scripts/workflow-yaml.ts` with `scripts/release-workflow.test.ts`, because the test imports it. Nothing is staged. Check `git status` for staged entries before an explicit-path commit.
