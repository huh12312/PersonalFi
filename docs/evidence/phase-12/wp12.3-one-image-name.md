# WP 12.3: One image name and the pull-first install

**Request.** `docs/research/13-docker-hub-publishing.md` §4 (the install side), and the follow-ups WP 12.2 left (`wp12.2-dual-registry-release.md` §6): the verifier's cosign v2 fallback, the stale `org.opencontainers.image.source` label, and the chi floor. Before this package, one image had three names: `personalfi/api:<sha>` when built locally, `ghcr.io/huh12312/personalfi-api:<version>` when published, and the verifier re-tagged the published one back to the local name.

**Result.**

1. **One name per image.** compose.yml runs `${REGISTRY:-ghcr.io/huh12312}/personalfi-{api,backup,proxy}:${PERSONALFI_VERSION:-dev}`. This is exactly the name `release.yml` publishes. Every other place that names an image follows (§1). The api image still serves api, worker and migrator. A source build is named `ghcr.io/huh12312/personalfi-api:dev`. `dev` is a tag no release carries.
2. **A local build can never pose as a release.** The new `scripts/build-name-guard.sh` runs before `just build` and before `just upgrade`'s build step. It refuses to build `personalfi-*` under `ghcr.io/huh12312`, `masterhuh` or `docker.io/masterhuh` with a tag shaped like a published one (`x.y.z`, `x.y`, `latest`, `sha-<7>`).
3. **`scripts/verify-release.sh` changes:**
   - `--source ghcr.io/huh12312|docker.io/masterhuh`. GHCR is the default, and `masterhuh` is accepted as the short form of the Hub mirror.
   - `--strict`. `gh` is now optional: without it, or when it is logged out, the attestation half is skipped with a printed warning, and `--strict` refuses instead.
   - The cosign fallback is **v3.1.4 by digest**.
   - The re-tag step is gone, and `--registry`/`--version` are removed (using them now fails with a message). `--pull` pulls by digest, then pulls the tag, and requires the tag to still name the verified digest.
   - The self-test's positive control is a real image that a GitHub workflow signed keyless with cosign v3: trivy v0.74.0, which the repository already pins (§2).
4. **`just install-release x.y.z`** (new) refuses anything but `x.y.z`, then runs `PERSONALFI_PULL=1 PERSONALFI_RELEASE=x.y.z just upgrade`. Pull mode then:
   - requires compose to resolve exactly `<REGISTRY>/personalfi-<image>:x.y.z` for all six PersonalFi services;
   - passes `REGISTRY` to the verifier as `--source`;
   - adds `--commit` only from a git checkout. A release tarball has no `.git`, and its images are then bound to the tag alone;
   - runs `docker compose pull` for the images that are not PersonalFi's;
   - starts with `up -d --wait --no-build --pull never`.
5. **The production isolation guard** accepts a release `x.y.z` as `PERSONALFI_VERSION`, as well as a 40-hex SHA. It still refuses `dev`, `latest`, `x.y` and `v`-prefixed values. Without this, pull mode could never run on `personalfi-prod`.
6. **The labels and the chi floor.**
   - All three Dockerfiles: `source` and `url` are now `https://github.com/huh12312/PersonalFi` (it was `https://github.com/chris/personalfi`). `licenses` is MIT, `title` is the published name, and `description` starts with "PersonalFi".
   - `docker/caddy.Dockerfile` gains `CHI_VERSION=v5.4.0` with a `# renovate:` comment, the `ARG`, `--with github.com/go-chi/chi/v5@${CHI_VERSION}`, and a line in the build-info check. Renovate's group gains the module.
   - trivy at every severity: chi is gone, 7 → 6 findings (§4).
7. **The upgrade-test harness** builds each era under its own compose names: W0 as `pf-upgrade/api:d04669e`, HEAD as `pf-upgrade/personalfi-api:<sha7>-wp94`.
   - It now checks after the HEAD hop that every running service is on HEAD's name, and that W0's images still exist under W0's names.
   - `UPGRADE_TEST_OVERLAY` lets an uncommitted package carry named files into HEAD's tree.
   - `upgrade-test.yml`'s trivy step scans the new HEAD names.
   - `bash scripts/upgrade-test/run.sh --path direct --ci`: **PASS** on the second run. The first run failed one restore check while this package was building images on the same host (§5).
8. **The pull path, end to end, against a throwaway local registry:**
   - a build under the new names, a push, and signing with a test-only cosign key;
   - the real verifier refused the key-signed images, as designed;
   - with a test-only shim that maps release.yml's identity to the test key, `just install-release 0.10.0` verified, pulled by digest and reached `docker compose up --no-build --pull never`. A healthy stack ran the verified digests under the published names, with nothing built (§3).
9. **Docs.**
   - README: Install is pull-first, followed by "Build from source (developers)". Upgrade shows pull mode first. "What is supported" and the host table are updated.
   - RUNBOOK: "Install a published release (pull-first)" and "Build from source" in First install; Upgrade with pull mode first; the verified-pull paragraph with `--source`, `--strict` and the cosign v3 note; the Docker Hub paragraph; the proxy pin table; isolation rule 2.
   - Also updated: `.env.example` (`REGISTRY`, `PERSONALFI_VERSION`), SECURITY.md, the Hub README, the release notes under `## v0.10.0 (in preparation)`, and 13 §7 row 12.3.
10. **Eight sabotages** (S1 to S8, one with a second part, S4b), each red and restored byte for byte, `cmp` clean (§6).

**State of the tree.** Uncommitted on `main`. HEAD was `53413c4` at the start. The orchestrator landed `ce182ac` and `5cace90` (web test and log only) during the work. Nothing of this package is staged or committed, and the 16 phase-10 PNGs were not touched.

### 1.1 Why `REGISTRY` defaults to GHCR, and what a source build is called

- **The community path needs no edits.** With the default, `.env` needs only `PERSONALFI_VERSION=0.10.0`.
- **The task's other option made the common path worse.** It was a `personalfi` default, with an override for pulls. That would have made every pull install set two variables, and a source build `personalfi/personalfi-api:dev`.
- **Source builds keep a published-looking name, safely.** They are named `ghcr.io/huh12312/personalfi-api:dev`, and the guard keeps the published tag shapes for verified pulls. `REGISTRY=personalfi` remains available, and the README says so.
- **The production clone, which builds from source at a commit,** builds `ghcr.io/huh12312/personalfi-api:<sha>` at its next upgrade. If its `.env` sets `REGISTRY=personalfi`, it builds `personalfi/personalfi-api:<sha>`. Its old `personalfi/api:<sha>` images are then unused. The release note and RUNBOOK say to remove them by name, never by prune.

## 2. The verifier

### 2.1 Flags

```text
bash scripts/verify-release.sh --release X.Y.Z [--source ghcr.io/huh12312|docker.io/masterhuh|masterhuh]
                               [--commit <40-hex>] [--pull] [--strict] [--owner …] [--repo …]
bash scripts/verify-release.sh --self-test
```

The order of the checks:

1. **The release.** It must be `x.y.z`.
2. **The source.** The source is validated as a registry/namespace. A source other than the two published ones prints a note and is read the same way.
3. **`gh`.** If `gh` is absent or logged out, the run refuses under `--strict`; otherwise it prints a warning and skips the attestations.
4. **Each image, by digest.** For each image: resolve the tag to a digest once, run `cosign verify` with `--certificate-identity https://github.com/huh12312/PersonalFi/.github/workflows/release.yml@refs/tags/vX.Y.Z` and `--certificate-oidc-issuer https://token.actions.githubusercontent.com` (plus `--certificate-github-workflow-sha` with `--commit`), then `gh attestation verify`. The identity is unchanged from WP 9.11.
5. **Only when all three images pass,** and only with `--pull`: for each image, `docker pull <ref>@<digest>`, then `docker pull <ref>:<release>`. Their image IDs must be equal. Otherwise the tag is removed and the run refuses.

### 2.2 The cosign pin: v3.1.4, and why

```text
COSIGN_IMAGE="ghcr.io/sigstore/cosign/cosign:v3.1.4@sha256:0f06154836d2de34f887a5c273506d52ca43edaa1d9e53e6510fa78a48f69c2d"
```

- **Why v3.** `release.yml` signs with cosign-installer v4.1.2's default, cosign v3.0.6 (12.2 §3). Its `sign` writes the new Sigstore bundle as an OCI referrer. cosign **v2.6.1**, the old fallback, reads only the legacy `sha256-<digest>.sig` tag. Against a real v3 keyless signature it reports `no signatures found`, as the S7 sabotage below shows. The old fallback would have refused v0.10.0.
- **Why v3.1.4 and not the signer's v3.0.6.** `gh api repos/sigstore/cosign/security-advisories` lists **GHSA-fx35-mq7g-6g98, HIGH, "Verification bypass via public key in legacy bundle", patched in v3.1.3 / v2.6.5** (2026-08-06). A verifier must not sit below that fix. v3.1.4 (2026-10-20, `GitCommit 0e48502c…`) is the newest release. It is 12 days old, past the repository's seven-day age.
- **The digest** is the multi-arch index (amd64, arm64, arm/v7, s390x, …), as `docker buildx imagetools inspect` reads it.
- **For the orchestrator:** `release.yml`'s own `verify` job uses the signer's cosign v3.0.6, which is inside the advisory's affected range. That is release.yml's to change, not this package's (§7).

### 2.4 `gh` optional, not "via the cosign bundle"

### 3.2 The real verifier refuses them, as designed

The verifier's container fallback has no host network, so it cannot reach `127.0.0.1:5001`. A **transparent** wrapper on `PATH` (`~/.cache/wp123-work/shim-transparent/cosign`) runs the same pinned image with `--network host` and passes the arguments through unchanged. The local tags had been removed first.

```text
$ bash scripts/verify-release.sh --release 0.10.0 --source 127.0.0.1:5001 --pull
verify-release: note: 127.0.0.1:5001 is not one of this project's registries (ghcr.io/huh12312 docker.io/masterhuh); its images pass only with release.yml's signature
verify-release: FAIL api: cosign verify refused 127.0.0.1:5001/personalfi-api@sha256:49dbb0dc…: error during command execution: no matching attestations: failed to verify log inclusion: not enough verified log entries from transparency log: 0 < 1
verify-release: FAIL backup: … (the same)
verify-release: FAIL proxy: … (the same)
verify-release: REFUSED: not every image verified; nothing was pulled
rc=1   (docker images: 0 images named 127.0.0.1:5001/*)
```

The key-signed bundle has no Rekor entry and no Fulcio certificate, so it fails before the identity comparison. In both cases the verifier accepts only a keyless signature that names release.yml. A key-signed image cannot pass it, whoever holds the key.
