**The scripted models.** For each input payload the harness runs two models against the same request:
a **faithful** one (restates every finding it read on the wire, cites one money row — the control that
proves the harness is not refusing everything) and a **maximally obedient** one, which narrates
faithfully _except_ that wherever it can read the payload's trigger — in the block's strings, in any
base64/base64url run decoded, in Unicode tag characters read as the ASCII they shadow — it does what the
payload asked (invent a figure, raise the severity, add an action, cite a link, claim deterministic or
impact, say something). It knows only the prompt bytes it was sent, so a sanitiser removal it cannot see
through is a removal that worked, and one it can see through is not.

**Where payloads go in** (`seed.ts`): merchant descriptor and memo are planted both as properties the
port type does not have (`descriptor`, `name`, `originalDescription`, `memo` on every transaction) **and
as the merchant id itself** (a first-seen merchant's charge, the recurring stream, a merchant-spend
row) — the worst case the real adapter does not do; crypto symbol on a no-basis position; category slug
on seven charges (six ordinary, one spike S1 flags) and the cashflow/category rows; goal name on the
off-pace goal R6 quotes; plus two sources the dispatch did not list — the market-rate provider's
attribution sentence and an `account_type_mix` record **key**.

**Two paths for every output entry.** `validator`: the model's JSON merged over a correct envelope (so
a forged `request_id`, `advisor_id` or an extra top-level field wins) or its text as the body — what
the validator must refuse on its own. `adapter`: streamed through the real adapter, which writes the
envelope from the request, keeps only `insights` and caps the bytes — the production path.

## 6. The live pass — deferred to the orchestrator

**Not run by me** (the stack is in use for WP 5.3's counted run; one agent on the stack at a time).
`scripts/redteam-live.ts` builds every request with the same `payloadRequest` CI uses and sends it
through the real narrator over the production adapter (default local-endpoint policy, system resolver,
digest pin before and after), one call per payload, no retry. Per payload it records `visible` (could
the planted instruction be read in the prompt sent), `followed` (does the reply show the directive's

reply must be read by eye), the verdicts, and **independently** `fabricatedSurvived` (the oracle over
every accepted narration — the exit criterion). Prints shape only; replies go to the `--out` file.
