# WP 11.6: Merchant display-name suggestions (`merchant.name`), narrow

**Request (Chris, verbatim).** 2026-10-19: "i think i need more LLM integration for the Insights Advisor, and then also to help with any non-deterministic categorization or enrichment needs." 2026-10-25: "Good with the llm proposal". 2026-10-26: "Good with proposal." WP 11.6 is package 11.6 of `docs/research/11-llm-integration-design-proposal.md` §5 (size S, after 11.2): §3.1's "Merchant display name for noise descriptors — model suggestion, narrow … the suggestion must be a substring-preserving cleanup, validated as such, not an invention", and §4's `merchant.name` row, "the descriptor only → {display_name: substring-preserving, or abstain}".

**Result.**

1. **Noise, decided deterministically.** `@ctx/ledger` gains `detectMerchantNoise`, a pure function of the bank's own text (never the holder's rename). It reuses the existing D25 rule first (`resolveMerchantIdentity(...).key === null`, the rule `pruneNoiseMerchants` applies, means a banking operation: never noise, never asked), refuses any descriptor whose identity came from the provider's own merchant name or entity, and then reads a seven-row shape table over the normaliser's residue (§1.1). The model is never called for a descriptor that is not noise: the listing only offers noise, and the composition re-checks every descriptor before anything is built.
2. **`merchant.name`, the narrowest query type.** Its own manifest, scope `transactions.residue` (no new scope, no contract bump), its own approvable shape with a versioned consent text folded in (`merchant-name-consent/1`), the narrator's kill ladder, one `advisor_runs` row per call with the payload digest and the payload retained for the inspector. Payload: the descriptor residue and the processor prefix the normaliser stripped — nothing else (§1.2).
3. **Local model only.** The descriptor crosses untokenised, so the query type runs only on the narrator's local model. With a hosted narrator no suggestion is made (`hosted_narrator`), there is no hosted adapter in `@advisor/local-model`, and `merchant_name_suggestions.llm_provider` is CHECK-pinned to `ollama` (§8 item 1).
4. **The validator, the whole point.** A reply is exactly `{display_name}` or `{abstain}`; a name must be a substring-preserving cleanup of the residue — every alphanumeric token, case-folded, equal to or a prefix of a descriptor token, in the descriptor's order, each descriptor token used once — at most 40 characters, no markup, link, digits-only name, copy-lint violation or unchanged residue. Ten named refusal classes (§1.3).
5. **Storage and provenance.** Migration `0063_merchant_name_suggestions` (expand-only, ledger-owned, one row per `(user_id, normalized_key)`, whole-or-none CHECKs). **Accept writes only through the `user_merchant_name` overlay** with `setTransactionOverlay`, the manual rename's own function, on every transaction of the merchant the holder has not renamed; `merchants.display_name` and `transactions.effective_name` are never written by a suggestion. Dismiss is final. Nothing is applied without Accept.
6. **The worker job** `insights.merchant_names`, nightly at 05:20 local, at most fifty merchants per holder, most-used first, deduplicated by key, never a key with a row (suggested, accepted, dismissed, refused) or a holder rename. **The api has no path to the model.**
7. **Routes.** `GET /merchants/name-suggestions` (open suggestions, the noise merchants not yet asked, and whether anything can be asked now and why not), `POST …/{id}/accept` and `POST …/{id}/dismiss` (session only, as the manual rename `PATCH /transactions/{id}` is). Preview and approval of `merchant.name` go through Advisor management's existing routes.
8. **The seventeenth control check,** `merchant_name_substring`: a fixed descriptor and a fixed reply inventing a brand; pass on `name.invented` (and on the same descriptor's honest cleanup being accepted).
9. **Evaluation and red team.** `scripts/advisor-eval.ts --merchant-name` over a 53-descriptor golden set (§4); `apps/api/test/redteam-merchant-name.test.ts` (seven probes).
10. **The web** (by the web sub-agent): the chip beside the bank's text on the transaction row and in the detail, keyboard-reachable Accept / Dismiss, the "not approved" note where the chip would be, the Advisors preview and approval, seventeen checks in the fixtures (§1.7).

**No live model was called.** Every model in this package's tests is the Ollama fake.

**State of the tree.** Uncommitted, on `main` at `d931707` (HEAD at the start; unchanged). Nothing staged by this WP. One migration, expand-only: `0063_merchant_name_suggestions.sql` (§5).

- **PNGs**: eight new `wp11.6-merchant-name-*` files from one targeted run (§6). ## 1. What was built

### 1.1 The noise detector (`packages/contexts/ledger/src/merchant-noise.ts`)

`detectMerchantNoise(providerFacts)` → `{noise: false, reason: 'no_merchant' | 'provider_named' | 'clean', key}` or `{noise: true, key, descriptor, strippedPrefix, shapes}`. `descriptor` is the identity's display (the normaliser's residue, as the holder reads it); `key` is the merchant's `normalized_key`; `strippedPrefix` comes from a new `processorPrefixOf` in `normalise.ts`, which walks the normaliser's own `PROCESSOR_PREFIXES` in the same order (and returns `null` when the prefix _is_ the merchant, `AMZN MKTP …`). `mayBeNoise(display)` is the cheap pre-screen over a stored `merchants.display_name`; it is never a verdict.

The order of the rules:

1. **D25 first** — `resolveMerchantIdentity({..., userMerchantName: null}).key === null` (a banking operation: `CHECK 1234`, `TRANSFER TO SAVINGS`, `PAYMENT THANK YOU`) → `no_merchant`. There is no merchant and no key to suggest for, and a model asked to name `CHECK` could only invent.
2. **The provider spoke** — identity source `provider_name` or `provider_entity` → `provider_named`.
3. **The shape table**, over the residue:

| Shape                | Rule                                                                                            | Example (residue)                |
| -------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------- |
| `processor_star`     | a `*` is still in the residue: a processor or aggregator wrapper the prefix table does not know | `Cko*patreon* Membership`        |
| `hash_token`         | a token of 6+ letters and digits with at least two of each: an order id or a hash               | `Ebay O*2k4tt1ff2`               |
| `reference_marker`   | a reference word (REF, REFNO, TXN, TRX, INV, ORDER, ORD, CONF, TRACE, ID) beside another word   | `Netflix REF XK2`                |
| `domain_tail`        | a token that is a web address or a path: `.COM`, `.NET`, `.ORG`, `.CO`, `.IO`, `.APP`, or `/`   | `Apple.com/bill`, `Cvs/pharmacy` |
| `vowelless_run`      | a token of 5+ letters with no vowel (A E I O U Y): a terminal's abbreviation                    | `Whlfds MKT`, `Strbcks`          |
| `run_together`       | the whole residue is one token of 12+ letters                                                   | `Bluebottlecoffee`               |
| `processor_squashed` | a processor prefix was stripped and one token of 6+ letters is left                             | `PAYPAL *EBAYINC` → `Ebayinc`    |

Not caught, on purpose: a cleanly truncated word (`STARBUCKS COF`). A suggestion may only drop, never complete, so there is nothing a model may do with it. Known over-firing: `processor_squashed` flags a clean one-word name behind a processor (`SQ *STARBUCKS`); the model's answer is then refused `name.unchanged`, recorded, never asked again (golden entry mn37).

Tests: `src/merchant-noise.test.ts` (37: the table with each example, twelve noise descriptors with residue/prefix/shapes pinned, thirteen non-noise with the reason, the provider-named cases, two fast-check properties — a banking operation is never noise whatever rides with it; a noise word makes a merchant noise and the key is the identity key — and the prefix hint).

### 1.2 The payload (scope minimisation)

`buildMerchantNameRequest` (`packages/contexts/insights/src/advisors/merchant-name/request.ts`) re-shapes through an explicit field list. The pinned snapshot (`test/wp116-merchant-name.test.ts`, a caller passing an amount, a date, an account id, a category and another merchant beside the two fields):

```json
{
  "granted_scopes": ["transactions.residue"],
  "snapshot": {
    "transactions_residue": {
      "descriptor": "Ebayinc",
      "stripped_prefix": "PAYPAL *"
    }
  }
}
```

The wire request adds only `request_id` (a fresh UUID per call, never a merchant's or transaction's), `deadline` and `max_response_bytes`; none of them reaches the prompt. The prompt's data block (`@advisor/local-model` `renderMerchantNamePrompt`) is `{"merchant":{"descriptor":…,"stripped_prefix":…}}` inside the one `<untrusted_data>` fence, through `sanitiseTree` and `escapeForBlock`; the system region is a constant and its hash is in the template hash. The api-db test reads every chat the fake received: three, one per noise merchant, each carrying exactly that block and none of `Blue Bottle`, `Joes`, `CHECK`, an amount, a date, a provider transaction id or the holder id.

**Scope choice.** `transactions.residue` (sensitivity 8, untokenised merchant words, `externalAllowed: false`, `bucketAmounts`) already names this class of data — the merchant words the deterministic tiers could not resolve — and is the narrowest in the vocabulary that covers a descriptor; `transactions.raw` is never sent. No new scope means no advisor-contract bump and no `snapshot_grants` CHECK change. No snapshot grant is required at run time (as for `insight.explain`'s own scope bound, the approval of the shape names the scope); the gate is the kind switch, the narrator (Off is off, hosted binds nothing), the advisor's own switch and quarantine, and the approval.

### 1.3 The validator (`reply.ts`) and its pinned table

Order of checks: schema → `name.empty` → `name.too_long` (> 40) → `name.markup` (`< > { } \` [ ] * # | \ _ ~ ^ =`or a control character) →`name.link`→`name.digits_only`→`name.copy`(the insight copy linter's banned phrases and merchant pseudonyms, field`evidence_label`) → substring preservation (`name.invented`/`name.out_of_order`) → `name.unchanged`. An abstention is recorded as status `refused`with class`abstained`; the model's reason is never stored or shown.

`manifest.ts` (`merchant.name` 1.0.0, `local_model`, scope `transactions.residue`, no impact, no narration, info, no triggers, 300 s ceiling, 4 KiB reply, the consent text and its sha256, `merchantNameShapeTemplateHash` folding template and consent), `request.ts`, `reply.ts`, `run.ts` (`runMerchantName`: gate → `advisor_runs` row with model and prompt hash → retained payload → call raced against deadline and watcher → barrier → validation; `merchantNameUnavailable` for the job's and the route's pre-check; a call failure or a schema refusal counts for the breaker, a name refusal does not), `preview.ts` (`previewMerchantName` over the holder's first noise merchant or an illustrative `Examplestore 7Q2Z9X4K`, `approveMerchantName` refusing `shape_changed`, `ensureMerchantNameAdvisor`), `jobs.ts` (`insights.merchant_names`, `insights.merchant_names_nightly`, `20 5 * * *`). The consent text (`merchant-name-consent/1`), shown in the preview and inside the approvable shape: "Merchant name suggestions run on the local model on this machine only. For a merchant whose name the bank sent as noise, the bank’s text as the app cleaned it, and the payment processor’s prefix it removed (if any), are sent to that model: no amount, date, account or category, and no other merchant. ## 5. Migration

`0063_merchant_name_suggestions.sql` (expand-only; a new table referencing only `users`; claimed in `packages/contexts/ledger/OWNERSHIP.md`, defined in `packages/contexts/ledger/schema/merchant-name-suggestions.ts`, listed in `packages/db/test/migrate.test.ts`):

```sql
CREATE TABLE merchant_name_suggestions (
  id               UUID         PRIMARY KEY,
  user_id          UUID         NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  normalized_key   TEXT         NOT NULL CHECK (normalized_key ~ '^[a-z0-9]+$' AND char_length(normalized_key) <= 256),
  descriptor       TEXT         NOT NULL CHECK (char_length(descriptor) BETWEEN 1 AND 200),
  stripped_prefix  TEXT         CHECK (stripped_prefix IS NULL OR char_length(stripped_prefix) BETWEEN 1 AND 32),
  status           TEXT         NOT NULL CHECK (status IN ('suggested', 'accepted', 'dismissed', 'refused')),
  display_name     TEXT         CHECK (display_name IS NULL OR char_length(display_name) BETWEEN 1 AND 40),
  refusal_class    TEXT         CHECK (refusal_class IS NULL OR refusal_class ~ '^[a-z][a-z_.]{0,47}$'),
  llm_provider     TEXT         NOT NULL CHECK (llm_provider = 'ollama'),
  llm_model        TEXT         NOT NULL CHECK (char_length(llm_model) BETWEEN 1 AND 200),
  run_id           UUID         NOT NULL,
  input_digest     TEXT         NOT NULL CHECK (input_digest ~ '^sha256:[0-9a-f]{64}$'),
  suggested_at     TIMESTAMPTZ  NOT NULL,
  decided_at       TIMESTAMPTZ,
  created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT merchant_name_suggestions_name_whole     CHECK ((status = 'refused') = (display_name IS NULL)),
  CONSTRAINT merchant_name_suggestions_refusal_whole  CHECK ((status = 'refused') = (refusal_class IS NOT NULL)),
  CONSTRAINT merchant_name_suggestions_decided_whole  CHECK ((status IN ('accepted', 'dismissed')) = (decided_at IS NOT NULL))
);
CREATE UNIQUE INDEX merchant_name_suggestions_key_idx ON merchant_name_suggestions (user_id, normalized_key);
```

(Each column CHECK is named in the file, `merchant_name_suggestions_*_check`; abbreviated here.) A first draft wrote the key CHECK as `{1,256}`, which Postgres refuses (a repetition count over 255); the ledger-db test caught it before anything else ran.

**Ownership: `@ctx/ledger`.** The key is a `merchants.normalized_key`; deciding which merchants are noise reads `merchants`, `transactions` and `transactions_provider`; and the only effect of an Accept is the `user_merchant_name` overlay through `setTransactionOverlay`. Any other owner would have to read three ledger tables directly, which `check-schema-ownership` forbids. `@ctx/insights` owns the query type and its run rows, as for every query type.

## 8. For Chris and the orchestrator

1. **The hosted-path decision: local model only, no hosted path built.** The descriptor crosses untokenised (the narrator's hosted path pseudonymises merchants; this cannot), so `merchant.name` runs only on the narrator's local model. With a hosted narrator the screen says "names stay on this machine" and nothing is asked. There is no separate hosted consent to tick because there is no hosted adapter; adding one later would be a new adapter, a consent text that says the raw descriptor leaves the machine, and a migration widening `llm_provider`'s CHECK.
2. **Scope reused, not added.** `transactions.residue` covers a descriptor residue; no contract bump. No snapshot grant is required at run time — the approval names the scope.
3. **Accept is per merchant, matching the manual rename's write.** The manual rename today is per transaction (`PATCH`) or a list (`POST /transactions/bulk`); Accept is the bulk form over every transaction of the merchant the holder has not renamed. A transaction of the same merchant arriving after Accept still shows the bank's text and the chip; Accept again renames it (the route is re-runnable on an accepted suggestion). No automatic carry-forward: that would be applying a name without a tap.
4. **An abstention is stored as `refused` with class `abstained`**, keeping the four statuses the brief named; a key the model declined is never asked again (a model change does not re-ask either — a narrow, conservative choice).
5. **Copy-lint false refusals.** "Best Buy" is refused `name.copy` (the linter's `buy`). Safe direction; the holder can rename by hand.
6. **The shape table over-fires on a clean one-word name behind a processor** (`SQ *STARBUCKS`): one wasted call, refused `name.unchanged`, never asked again.
