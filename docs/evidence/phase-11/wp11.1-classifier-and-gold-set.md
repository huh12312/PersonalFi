# WP 11.1: Deterministic classifier improvements, the gold-set replay, and "make this a rule?"

**Request (Chris, verbatim).** 2026-10-19: "i think i need more LLM integration for the Insights Advisor, and then also to help with any non-deterministic categorization or enrichment needs. do some deeper research there on what can be made deterministic for those actions and what shouldn't be." 2026-10-25: "Good with the llm proposal". 2026-10-26: "Good with proposal." WP 11.1 is package 11.1 of `docs/research/11-llm-integration-design-proposal.md` §5: the deterministic groundwork every later Phase 11 package measures against. **No model is called anywhere in this package.**

**Result.** The naive Bayes classifier gains three features (`mf:` MCC family, `p:` the provider's PFC primary, `dm:` day-of-month thirds) and a **re-derived calibration**: the new replay showed the old single curve let context-only guesses through the 60 % floor at 8 % precision, so a prediction that no word of the payee backs is now capped at a coin flip (it abstains), and payee-evidenced predictions use the slope the demo seed's replay fits (7, from 2.2). On merchants the model has never seen, the classifier's precision goes from **32 % to 88 %** at the same recall (§1). `scripts/categorization-eval.ts` / `just categorization-eval holder=…` replays the holder's hand-filed transactions through `decide()` leave-one-out, per tier and overall (precision, recall, abstain rate, top-10 confusion pairs), as stable JSON (`categorization-eval/1`) and a text table, on a read-only connection; the demo seed's figures are a CI regression snapshot with a 1-point tolerance. A built-in advisor `spending.rule_suggestion` proposes "make this a rule?" for a merchant filed the same way ≥ 3 times with no rule or locked default. The Inbox shows, under each uncategorised row, a one-line "why" read from the working the tiers **stored** when they decided (new table `category_abstentions` holds it where every tier abstained), never recomputed.

**State of the tree.** Uncommitted, on `main` at `ac6124c`. Nothing staged by this WP. Two migrations, both expand-only: `0053_category_abstentions.sql` (one new table) and `0054_snapshot_grant_scopes_v1_7.sql` (the advisor scope CHECK widened; §5).

**Not done by this WP, by design.**

- **`confirmAssignment` is never called by `apps/api`** (found here; ORCHESTRATOR line in the report). Every category the holder picks goes to the ledger overlay (`transactions.user_category_id`) only, so `classifier_examples`, learned merchant defaults and confirmed assignments stay empty on a real install: the classifier is cold and tier 3 never learns. This WP does **not** change any write path. The gold set and the rule-suggestion facts read the holder's answers from both places (`src/eval/holder-answers.ts`: the overlay wins; a confirmed assignment counts where there is no overlay), so the harness and the advisor work on a real install today. Wiring the overlay route to `confirmAssignment` would switch on tier 3 learning and the classifier for real data, which changes what syncs categorise: a decision for Chris, not a side effect of this package.
- **The account's management/role overlay is not a feature.** `CategorizableTransaction` does not carry it, and widening `@ctx/ledger`'s port for a feature that mostly separates accounts the `a:` type already separates was not cheap. Skipped, as the brief allowed.
- **Rows uncategorised before v0.9.16 have no stored working** until their next categorisation pass (a sync touching them). Their Inbox line says "No categorisation pass has recorded its working for this yet." Nothing is backfilled, and nothing recomputes a reason to fill the gap.
- **No model.** The harness's output shape is what 11.2 will read; nothing here calls one.
- **`~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets** were not read, listed, built or touched. No compose service was started. Database tests ran against the running dev cluster (`personalfi-dev-db-1`) in scratch databases (§2).

## 1. What was built

### 1.1 Classifier features (`packages/contexts/categorization/src/classifier.ts`, `engine.ts`)

| Feature                   | When present           | Note                                                                             |
| ------------------------- | ---------------------- | -------------------------------------------------------------------------------- |
| `t:<token>`               | always                 | payee tokens (unchanged)                                                         |
| `b:<n>` + `d:in\|out`     | always                 | the sign-magnitude bucket (unchanged)                                            |
| `a:<type>`                | account type known     | unchanged; the management/role overlay was **not** added (above)                 |
| `m:<leaf>`                | MCC present            | unchanged                                                                        |
| **`mf:<family>`**         | MCC present            | new: the top level of the MCC's category key (`0742` → `mf:family`)              |
| **`p:<primary>`**         | provider category sent | new: the PFC primary, lower-cased, only if it is code-shaped (`[a-z0-9_]{1,64}`) |
| **`dm:early\|mid\|late`** | always (date)          | new: days 1–10, 11–20, 21+                                                       |

`classifierFeaturesOf(input: DecisionInput)` (engine.ts) is now the **one** mapping from a transaction to its features: `decide` scores with it, `confirmAssignment` counts with it, the replay trains and grades with it. Every feature that moves a classifier decision is named in the stored chain's `detail` ("strongest signals: …") and in the tier's new `facts.signals`, which is what `explainAssignment` returns.

### 1.2 Calibration, re-derived

The old curve was `confidence = logistic(2.2 × margin)` for every prediction. Over the demo seed's replay (3 variants × 2 holdouts, every prediction the classifier would make with no floor), split by whether at least one payee token had been confirmed under the winning category:

| Prediction                                                        | n     | Right                                           | Old curve let through the 0.6 floor |
| ----------------------------------------------------------------- | ----- | ----------------------------------------------- | ----------------------------------- |
| payee-evidenced                                                   | 4,045 | 98.8 % (≥ 85.7 % in every margin bin from 0.08) | 3,967 at 98.9 %                     |
| **context-only** (amount, account, direction, MCC, PFC, day only) | 2,279 | **7.4 %** (≤ 11.4 % in every bin)               | **1,495 at 8.1 %**                  |

So the curve is two segments (`confidenceFromMargin(margin, payeeEvidence)`): payee-evidenced `logistic(PAYEE_MARGIN_SCALE × margin)`, capped at 0.99, with `PAYEE_MARGIN_SCALE = 7` — the maximum-likelihood slope fitted to the payee-evidenced predictions was 7.10, rounded down; context-only the same, capped at `CONTEXT_ONLY_CEILING = 0.5`, a policy rather than a fit (the seed's 0.07 is a property of a seed whose 32 merchants mostly sit in categories of their own; 0.5 is "no better than a coin flip", true everywhere). The default floor (0.6) and `MIN_MARGIN` (0.08) are unchanged; the classifier still abstains whenever it is unsure, and now names the gate (`code: cold | no_features | single_category | under_supported | too_close | below_floor`, with the figures). `test/gold-set.test.ts` re-runs the fit on every CI run and fails if the shipped slope is more than 10 % from it.

Read honestly:

- **The calibration is what moved precision**, not the features. On merchants it has never seen, the old classifier was confident and wrong two times in three; now it abstains on those and is right 88–100 % of the times it speaks, at about the same recall. That residue is exactly what 11.2's model suggestions will be offered for.
- **The new features did not help on the seed by themselves** ("features only" column): `dm:` costs 1–2 points on the transaction holdout (the seed's dates carry little category signal) and `mf:` costs a little on cold merchants (the synthetic MCCs are deliberately not one-to-one with the truth). Under the new calibration they cost nothing measurable and are kept because they are the signals 11 §3.1 names and real data (rent on the 1st, recurring bills, several merchants per family) carries more of them than the seed does. The snapshot will show the day a feature costs more than a point.
- With the provider's PFC present the waterfall is unchanged (the provider tier speaks first on every row).
- The seed's Phase 1 gate (`test/golden.test.ts`, ≥ 85 % on the honest configurations) still passes unchanged.

### 1.4 The gold-set replay (`src/eval/replay.ts`, `src/eval/load.ts`, `src/eval/holder-answers.ts`)

- `replayGoldSet(examples, {rules, lockedMerchantDefaults, confidenceFloor, merchantSupportThreshold, holdout})` — pure. Clears the overlay (tier 1 would grade itself), trains the classifier on every _other_ answer by subtraction (`withoutExamples`, proven equal to retraining by a 300-run property test), recounts the learned merchant default from the other answers (a **locked** default is kept: it is an instruction), uses every rule. Reports `waterfall` (per tier: reached, decided, correct, precision, recall, abstain rate), `isolated` (each tier alone on every row; the classifier through the same `classifierFeaturesOf` and `predict`), `overall` and the top-10 `confusion` pairs, rounded to four decimals, schema `categorization-eval/1`. `formatReplayReport` prints the fixed-width text table.
- Holdouts: `transaction` (one answer at a time) and `merchant` (a whole merchant at a time: the cold case, and the figure 11.2 gates on).
- `loadGoldSet(executor, ledgerPort, userId)` reads the holder's answers (overlay first, confirmed assignments where no overlay), the rules and the locked merchant defaults. `SELECT`s only.
- CLI: `apps/api/src/bin/categorization-eval.ts` (the copy the image ships), entry point `scripts/categorization-eval.ts`, recipe `just categorization-eval holder=… [json=true]`. Every connection opens with `default_transaction_read_only = on` (login role, not the app role: the app role's grants are re-asserted by a write at boot, and the read-only session is the stronger promise). Output: counts, ratios and category keys; never a payee, amount or id (asserted).
- The demo seed's labelled set is a CI regression (`test/gold-set.test.ts`, unit project): the six variant/holdout figures above, overall and classifier-alone, fixed with `TOLERANCE = 0.01`; a drop beyond it fails, a rise beyond it fails with "raise the snapshot", and the tolerance itself is pinned.
- Dev run against `personalfi_dev`: the database has no holder, so the recipe prints "no account holder exists." The end-to-end run is the api-db test, against a synced, hand-filed scratch install (§2).

### 1.5 The Inbox "why" (`src/explain-line.ts`, `src/explain.ts`, migration 0053, `GET /transactions/explanations`)

- Each tier's chain entry now carries `facts` (rule: rules/matched; merchant: support/needed; provider: sent; classifier: code, confidence, floor, examples, payee evidence, signals). `explanationLineOf(chain)` composes the line **from the stored chain only** ("Every tier abstained: none of your 4 rules matched, merchant confirmed 1 of 3 times needed, no bank category, classifier 41 % below its 60 % floor."), falling back to each tier's stored `detail` for chains written before this WP.
- `category_abstentions` (0053): when every tier abstains on a transaction with no assignment, `categorizeTransactions` stores the chain there (rewritten only when it changes, so `decided_at` is when that working was first recorded; deleted when an assignment is written or confirmed; never by a preview). `category_assignments` was untouched: its source CHECK has no `none`, and "uncategorised" rows there would have changed every reader of that table.
- `explainTransactions(executor, {userId, transactionIds})`: the current assignment's chain, else the abstention's, else `not_recorded`. `GET /transactions/explanations?ids=…` (≤ 200; non-UUIDs dropped; session required) returns `{transactionId, status, source, categoryKey, confidence, decidedAt, line, tiers}`. OpenAPI and the web SDK regenerated.

### 1.6 The rule-suggestion advisor (`packages/contexts/insights/src/advisors/builtin/rule-suggestion/`)

Built by the advisor sub-agent; wiring of the two on-demand routes and the health route closed by me.

- **Scope** `categorization.rule_candidates` (19th member of `ADVISOR_SCOPES`, advisor contract **1.7.0**, strictly additive; the published v1 schemas regenerated: request +79 lines, manifest +5, response +2). Catalogue row: sensitivity 4, `externalAllowed: false`, no per-run consent, merchants tokenised. Migration `0054_snapshot_grant_scopes_v1_7.sql` widens `snapshot_grants_scope_check` (0029's DROP + ADD shape); `apps/api/test/phase3-registration.test.ts` checks parity.
- **Snapshot block** `rule_candidates.merchants[≤ 64]`: `merchant_ref` (always a `MERCHANT_…` pseudonym, D22), `category_ref`, `category_slug`, `confirmations`, `covered_by_rule`, `locked_default`, `transactions[1..8].transaction_ref` (objects, so every evidence ref ends in an entity leaf the mentions and the web resolver read). Port `CategorizationPort.listRuleCandidates` (fake `inMemoryCategorizationPort`), builder arm `#ruleCandidates`; api `createInsightsCategorizationPort` over `@ctx/categorization`'s `listRuleCandidates`, bound in the worker's `insightsModule`, `POST /advisors/run`, the payload preview and the health route.
- **Facts** (`@ctx/categorization` `listRuleCandidates`): every (merchant, category) pair filed by hand ≥ 2 times (deliberately below the advisor's threshold, so the threshold is what a test sees refuse 2), newest transactions first; `coveredByRule` is `decide()` itself, rules only, on the newest one; `lockedDefault` from `merchant_profiles`.
- **Advisor** `builtin.spending.rule_suggestion` (catalogue `RS1`, wave spending, P3, enabled by default; max severity info; no impact; `maxInsights` 10). `RULE_SUGGESTION_MIN_CONFIRMATIONS = 3`; skips `covered_by_rule`, `locked_default`, and (one policy beyond the brief, tested) a merchant filed two different ways, so "the same way" stays true. One insight per merchant: key `spending.rule_suggestion.<MERCHANT token>`, period `all_time`, title "A merchant you keep filing the same way", summary "You have filed this merchant under {category_slug} {n} times by hand. A rule would file it there automatically from now on — nothing changes until you save one." Evidence: the count (metric citing `…confirmations`), the category (citing `…category_ref`, value the uuid), one row per filed transaction (citing `…transactions[j].transaction_ref`, value the uuid). `proposed_actions: [{kind: 'create_rule_draft', label: 'Create rule', …}]`. The `ProposedAction` schema is strict and has no payload field and was **not** changed: the drafted rule (merchant → category) is carried by the evidence, which the web resolves. Ranks below every impact-bearing insight and last in the catalogue budget. Dismissal is the existing per-`(advisor_id, key)` ladder, so per merchant (30 / 90 days / permanent).
- The holder's merchant name never appears in the insight (D22); the web shows it from the cited transaction.
- **For Chris on first use:** like every built-in, it runs only once its scope is granted (Settings, Advisors; `PUT /advisors/{id}/grants`). Registration is automatic at boot; the grant is not, by the house rule (`modules.ts`, `registerBuiltinAdvisors`).

Built by the web sub-agent.

- Known, left as is: the card's existing **Accept** button still accepts a suggestion without creating a rule (existing behaviour for every insight).
