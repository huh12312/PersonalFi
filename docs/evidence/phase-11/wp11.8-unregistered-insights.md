# WP 11.8: An install without `advisor_token_secret` says so, and an idle filtered consumer is not "behind"

**Request.** Two defects found on the production install on 2026-10-31 (execution log, the entries after the upgrade to `3679a31`):

1. Production ran three weeks with `secrets/advisor_token_secret` an empty placeholder. `insightsModule` (`apps/api/src/modules.ts`) feature-detects that secret and registers `module.insights`' events only (by design, `packages/config/src/schema.ts`), so the worker never ran a narration, a Brief, a control check, Ask or the advisor. The api's narrator runtime exists in preview mode regardless, so Settings → Language model let the holder pick a hosted provider, tick consent and save a key, `GET /advisors/module/enabled` read "on", and "Run control checks" was offered. The soak report read the Brief criterion "not started".
2. `pumpBatch` (`packages/platform/src/events/pump.ts`) advanced a filtered consumer's `last_seq` only when it handled a matching event. A consumer whose filter matched nothing stayed at its first offset, and `outboxHealth` counted the whole outbox as its lag: 763 on production. Past `READINESS_MAX_OUTBOX_LAG_EVENTS` (1 000), `/ready` would read `degraded` for no reason.

**Result.**

1. **One source of truth for registration.** `apps/api/src/module-registration.ts` has `insightsRegistered(source)`, a type guard over the secret's presence. `insightsModule` itself now asks it, so the worker's wiring and every api surface run the same function on the same config value. Nothing reads the database.
2. **`/ready` gains a `modules` line**, on both 200 bodies (with and without the platform half). It names every `MODULE_FLAGS` flag, in order, with `registered`, and the `reason` when false. It is informational: the 503 rules and the `degraded` rules are unchanged.
3. **`GET` and `PUT /advisors/module/enabled` gain `worker: { insightsRegistered, reason }`** (additive). `effective` keeps its meaning (operator half and holder half).
4. **The Language model card and Advisors** show a non-dismissable notice when the module is not registered: "The insights module is not enabled on this install: the operator has not written `advisor_token_secret`. Narration, the Brief, Ask and the advisor will not run until it is.", with a link to [RUNBOOK › Enabling the insights module](../../../RUNBOOK.md#enabling-the-insights-module). The provider, consent and key controls stay usable. **Run control checks** is `aria-disabled`, described by the notice, and never posts.
5. **The control checks.** The "Kill switches 1 and 2" row's level-1 line ends "the worker's insights module is registered" or "is NOT registered: advisor_token_secret absent". `POST /narrator/control-checks` answers 503 `insights.advisor_token_secret_unconfigured` and `just genai-selftest` exits 78 (config) with that sentence. Each refuses before anything is started or enqueued.
6. **The soak report**'s Brief row reads "insights module not registered on the worker (advisor_token_secret absent)" when that is why there are no Briefs. The report does not read readiness, so it reads the mounted secrets in its container by the config loader's own rule (`readOptionalSecret`, now exported from `@core/config`). It hands the answer to the same `insightsRegistered`. It never reads the database for this.
7. **The pump advances a filtered consumer past events it would skip.** The advance stops at the highest `seq` visible in the same statement that proves none of the skipped events matches. It never moves past a matching event and never moves a `failed` or `paused` consumer. It runs in its own transaction and writes no receipt. The rule and why it is safe are in §1.3.
8. **Docs.** RUNBOOK: "Create secrets" opens with "Read this first: `advisor_token_secret` turns the whole insights module on". The "Language model" section opens with "Enabling the insights module", which carries the exact `sudo sh -c` line, why a plain redirect fails, and "never rotate once set". The readiness troubleshooting note covers the idle-consumer fix. Release notes `## v0.9.27`; 11 §5 row 11.8.

**No migration.** None was needed. Migrations 0001–0063 are untouched.

**State of the tree.** Uncommitted, on `main` at `33bdb1b` (HEAD at the start; unchanged). Nothing is staged. The 16 phase-10 PNGs (`wp10.3-*` modified, `wp3.11-*` untracked) were not touched.

### 1.3 The pump's safe advance (`advancePastUnmatched`)

**When it runs.** After `pumpBatch`'s filtered select returns no rows, or returns a short batch that was handled in full. It is one statement inside `db.transaction`:

```sql
WITH head AS (SELECT max(seq) AS seq FROM domain_events)
UPDATE event_consumer_offsets o
   SET last_seq = head.seq, updated_at = now()
  FROM head
 WHERE o.consumer_name = $name
   AND o.status NOT IN ('failed', 'paused')
   AND head.seq > o.last_seq
   AND NOT EXISTS (SELECT 1 FROM domain_events e
                    WHERE e.seq > o.last_seq AND e.seq <= head.seq
                      AND e.event_type = ANY($filter))
RETURNING o.last_seq
```

**Why it is safe.** The codebase already has an ordering rule, and the advance uses it rather than a time grace. `append_domain_event` (migration 0003) takes the `PFEVTSEQ` transaction-scoped advisory lock _before_ it draws `nextval`, and holds it to commit. So `seq` order is commit order. Any event not visible to a snapshot, whether drawn by a transaction still open or not drawn yet, has a higher `seq` than every visible event. "A lower seq commits after a higher one" cannot happen while every append goes through that function, and 0003 makes it the only write path ("no way to insert an event that bypasses it, including from psql").

The maximum and the no-match proof are read in **one statement**, so from one snapshot. The visible maximum is therefore exactly the committed prefix, and the proof covers every event the advance moves past. No `recorded_at` grace is needed, so none was added.

What it must never use is the sequence's own high-water mark: that includes a `seq` drawn by an uncommitted transaction. Sabotage S3 uses exactly that and is caught (§3).

**What it does not do.** It runs no handler, writes no `processed_events` receipt and touches no failure column. It re-reads `status` under the row lock rather than trusting the batch's read.

**Metrics.** An idle advance marks the consumer so the loop publishes the lag gauge, which used to be published only after a handled event.

**`pump-filtered-idle.test.ts`** (5 tests, own scratch database `wp118_pump_filtered_idle`):

- **30 non-matching events, one `runConsumerOnce`.** Nothing is handled, there is no receipt, and `last_seq` is the last of them. `outboxHealth` gives lag 0, oldest unprocessed `null` and `maxLagEvents` 0. Then one matching event: handled, lag 0. Then trailing non-matching events: the same pass that handles a short batch also advances past them.
- **The ordering hazard.** Transaction 1 appends a matching event (seq N) and stays open, holding the `PFEVTSEQ` lock. Transaction 2's non-matching append queues behind the lock. A pump pass advances only to the last _visible_ event (< N). Once both commit (transaction 2 gets N+1), the next pass delivers N and ends at N+1, lag 0.
- **A matching event committed while the batch is being handled** (by another connection, from inside the handler) is not skipped by that pass's advance. `last_seq` stays at the handled event, and the next pass delivers it.
- **Paused and failed consumers** are never advanced: lag stays 8.
- **A matching event whose handler refused** (in backoff) is never passed. Once the handler accepts, it is delivered, then the rest are skipped, lag 0.
