# WP 11.2: Category suggestions for the abstained residue, from a local model, never applied

**Request (Chris, verbatim).** 2026-10-19: "i think i need more LLM integration for the Insights Advisor, and then also to help with any non-deterministic categorization or enrichment needs." 2026-10-25: "Good with the llm proposal". 2026-10-26: "Good with proposal." WP 11.2 is package 11.2 of `docs/research/11-llm-integration-design-proposal.md` §5, under the decisions of 2026-10-25/26: categorisation on the local model only by default (D22; a hosted provider only under a separate consent naming merchant names, shipped unticked and off); suggestions off until the gold-set replay shows ≥ 85 % precision on the holder's own history, the chip always showing the reason; the model choice measured and picked in Settings.

**Result.** (1) **Picks teach.** Every category pick — `PATCH /transactions/{id}`, `POST /transactions/bulk`, and Confirm on a suggestion, which is the same PATCH — now appends `ledger.TransactionCategoryChosen` in the overlay's own transaction; the categorization consumer learns from it (`learnFromPick` → `recordConfirmation`, extracted from `confirmAssignment`), so `classifier_examples` and the learned merchant default grow on a real install. `just categorization-learn-backfill holder=…` replays standing picks once, idempotently, with counts. (2) **`categorize.suggest`**, a second `local_model` query type: its own manifest, a new scope `transactions.residue` (advisor contract 1.8.0), its own payload preview and approval shape, the narrator's kill ladder, a run-inspector row per batch with its digest, a closed-enum reply validator, and a worker job after a sync's categorisation pass that asks the model about each uncategorised merchant once per taxonomy version. (3) Suggestions land on the abstention row (migration 0055), never as an assignment; the Inbox and transaction list show "Suggested by the model: <Category> — <reason>" with Confirm and Not this. (4) Settings → Language model → Category suggestions: the model choice (the narrator's pin or a second pin `LOCAL_MODEL_CLASSIFIER_*`), preview and approve, **Measure** (the gold-set replay with the model as a seventh tier on the residue, in the worker), and **Enable**, refused below 85 % over 20 scored rows. The 10.16 self-test gains `suggest_enum_refusal`. **No live model was called**: every model in this package's tests is the Ollama fake or the vendor fake; Chris's first Measure is the live check.

**State of the tree.** Uncommitted, on `main` after `dbb4c8b`. Nothing staged by this WP. Two migrations, both expand-only: `0055_category_suggestions.sql` and `0056_snapshot_grant_scopes_v1_8.sql` (§5).

**Not done by design.**

- **The measurement table has no live figures** (§1.7). No live model call was allowed; the figures below are the fake's. The live numbers for the narrator's pin and a classifier pin are the first Measure on Chris's install.
- **Tiers 3–5 still do not reach the ledger's effective category.** `@ctx/ledger`'s `resolveCategoryId` is `user ?? rule` (WP 1.4); a learned merchant default, a provider PFC or a classifier decision is recorded in `category_assignments` only, which no list, Inbox filter, budget or report reads. §1 makes tier 3 and the classifier _learn_; whether what they decide is _shown_ is a separate, pre-existing gap (ORCHESTRATOR line in the report). The suggestion residue is unaffected: it is the rows every tier abstained on.
- **A pick on a split line teaches nothing** (`setTransactionSplits` writes per-line categories, not the overlay); **clearing a pick** (`categoryId: null`) emits nothing and leaves the confirmed assignment it taught.
- **Off means off for suggestions too**: kill level 2 is the narrator's per-holder configured view, so a holder whose narrator is Off gets no suggestions even with the classifier pin chosen.
- **Batches are fifteen merchants, not fifty.** The ceiling is 50 (`SUGGEST_BATCH_MAX`, enforced at three layers); 15 is what fits the local reply budget (`num_predict` 1 024 ≈ 50 tokens per suggestion with its reason — the adapter sub-agent's measurement), so a full batch is never cut mid-reply. Raising it means raising `num_predict`, which shrinks the prompt that fits, or a per-model generation override.
- **No automatic backfill**, as the brief says; the recipe is the holder's decision.
- **Measure needs an approved payload.** The measurement sends the holder's residue to the model, so it honours the approval like a run (it skips only level 3's switch and the gate it exists to open). Without one it records a failed measurement (`payload_not_approved`); the card says nothing is asked for until the payload is approved, but does not disable Measure.
- **`just genai-selftest` (the CLI) binds no suggestion model**, so `suggest_enum_refusal` reads "not applicable" there; the worker's self-test (Settings) binds it.
- **Leftover scratch databases are not this WP's.** The one read-only check at the end (§6) found no `wp112*` database; 37 other `personalfi_*` scratch databases remain on the dev cluster (`personalfi_api_wp412bc7v2_*`, `…_p3wire_*`, `…_wp111_rulesug_*`, `personalfi_catg_consumer_*`, `…_seeding_*`, …). Nothing was dropped.
- **`~/personalfi-prod`, project `personalfi-prod`, its volumes, images and secrets** were not read, listed, built or touched. No compose service was started; the `ollama` container and its volume were not touched.

## 1. What was built

### 1.1 The learning path (§1 of the brief)

- `@ctx/ledger` `setTransactionOverlay` appends **`ledger.TransactionCategoryChosen`** `{transactionId, categoryId, previousCategoryId}` when the patch sets `userCategoryId` to a new non-null value (registered in `LEDGER_EVENTS`). The PATCH route now runs in one transaction (the bulk route already did), so the pick and its event commit together.
- `@ctx/categorization`'s consumer (`categorization.assignments@v1`, name unchanged: no replay from 0) filters the new type and calls `learnFromPick`, which re-reads the transaction through the port and refuses to trust the event: `stale` if the overlay no longer says that category, `already_learned` if the current assignment is a confirmed `user` row for it (a redelivery, a replay or a second backfill counts nothing), `unknown_category` for Uncategorised or a category the holder no longer has; else `recordConfirmation` — the three writes `confirmAssignment` always made (user assignment, classifier examples through `classifierFeaturesOf`, merchant default with `MerchantDefaultLearned` at the crossing), now shared and accepting the holder's own categories.
- `backfillLearningFromPicks` + `apps/api/src/bin/categorization-learn-backfill.ts` + `scripts/categorization-learn-backfill.ts` + `just categorization-learn-backfill holder=… [json=true]`: every standing overlay pick through the same `learnWithin`, transaction-id order, counts only (`picks`, `learned`, `already learned`, `skipped`).

### 1.2 The residue payload (scope `transactions.residue`, minimisation)

`residueFeaturesOf(decisionInputOf(transaction))` reads the row **off `classifierFeaturesOf`** — the MCC leaf dropped — so a field the classifier does not see cannot reach the model. `@ctx/insights`' `buildSuggestRequest` re-shapes each row through an explicit field list under a batch-local ref. ### 1.3 `categorize.suggest` (`packages/contexts/insights/src/advisors/suggest/`)

- **Manifest** `categorize.suggest` 1.0.0, kind `local_model`, scope `transactions.residue`, no impact, not narrates-only, info at most, no triggers, 300 s ceiling. Registered as an `advisors` row (default off) by `registerBuiltinAdvisors`, **not** in the registry the nightly fan-out iterates.
- **Shape and approval** `categorySuggestShape(templateHash)` = `queryShape` over advisor id, version, kind, scopes and the suggestion template hash; `previewCategorySuggest` builds the request through the run's own constructor over the residue a run would send now and renders the prompt through the model's pure `render`; `approveCategorySuggest` writes `advisor_payload_approvals` with provider and model, refusing `shape_changed`.
- **Run** `runCategorySuggest`: gate through `decideContinue` — level 1, level 2 (`advisors.kind.local_model` and a model bound for this holder), level 3 (`advisors.enabled` **and the precision gate and the scope grant**), the approval; `advisor_runs` row with the prompt hash, model and the batch's `canonicalRunDigest` before the call, payload retained 30 days (`inspectRunPayload` re-derives it); the call raced against the deadline and the watcher; the barrier re-reads every switch; a failed call or a reply outside the format counts for the breaker (3 consecutive → quarantine), a refused row does not (a hostile merchant name must not switch the feature off). `measureCategorySuggest`: the same gate less level 3's enabled bit and the precision gate (what a measurement exists to open), the same request, call and validator, **no write**.
- **Validator** `validateSuggestReply`: schema pin (exactly `{suggestions:[{transaction_ref, category_key, reason}], abstain:[ref]}`, else the whole reply is `schema`); `unknown_ref`, `duplicate_ref`, `missing`; **`unknown_category`** against the holder's keys as sent; the reason 1–140 characters, `reason_numeral` (any `\p{Nd}` digit, or a scale/currency word), `reason_link`, `reason_markup`, `reason_copy` (the insight copy linter: banned phrases, imperative advice).
- **Self-test** `suggest_enum_refusal` (worker side, twelfth check): the suggestion adapter's control probe asks for `control.outside_taxonomy` on a synthetic one-row request; pass when the validator refuses it (or the model declines), fail if any key outside the list survives; not applicable with no suggestion model.

### 1.4 The model call (`@advisor/local-model` `src/suggest.ts`, by the adapter sub-agent)

`renderSuggestPrompt` (constant system region; every string, keys and labels included, through `sanitiseTree`; one `<untrusted_data>` fence; `<`/`>` escaped), `SUGGEST_FORMAT`, `SUGGEST_PROMPT_TEMPLATE_HASH`, `createLocalSuggestionAdapter` (the narrator's endpoint policy, digest pin before and after the chat, warm-up headroom rule, timeout = min(`LOCAL_MODEL_TIMEOUT_MS`, deadline), byte cap, abort counter, ≤ 50 rows and refs `r1…r99` refused otherwise), `createHostedSuggestionAdapter` (the narrator's egress allow-list, budget, key handling and error mapping through a `createHostedCaller` extracted from `hosted.ts`; the narrator's request bytes pinned unchanged per provider), `controlProbe('suggest_enum')`. 42 tests in `test/suggest.test.ts`.

### 1.5 The composition (`apps/api/src/category-suggestions.ts`)

- `createSuggestionRuntime` resolves through the narrator runtime's per-holder `resolve(userId)` and the same `NarratorStores`: the narrator's pinned local model (environment over Settings, as for the narrator) or the classifier pin on the same endpoint; **a hosted narrator only when the separate suggestion consent covers today's text** (`hosted_consent_required` otherwise), then the narrator's own consent and key. Preview mode (api) builds rejecting transports.
- `categorization.suggest` job (worker, concurrency 1, deduped per holder, enqueued a minute after a sync pass that recorded new residue, in the pump's transaction): exits without a run row if the advisor is off or the gate shut; applies cache hits; asks misses in batches of 15, at most 20 batches a job; records answers. `categorization.suggest_measure`: `loadGoldSet` → `measurementResidue` (the replay with merchant holdout, via a new observation-only `onDecision` hook on `replayGoldSet`) → batches → `scoreMeasurement` → one `category_suggestion_evals` row.
- The separate consent text (`category-suggestions-hosted/1`): "Category suggestions on a hosted provider: merchant names leave this machine. For every uncategorised merchant, its payee words, the kind of card or account, the direction, an amount band and the part of the month are sent to the hosted provider you chose for the narrator, under your key. Nothing is filed until you tap Confirm. …"
- Config `LOCAL_MODEL_CLASSIFIER_NAME`/`_DIGEST` (both or neither, digest shape-checked; `.env.example`, `compose.yml` api + worker).

`GET|PUT /categories/suggestions/settings`, `GET /categories/suggestions/preview`, `POST /categories/suggestions/approve`, `POST /categories/suggestions/measure` (202), `POST /categories/suggestions/enabled` (409 `categorization.suggestions_below_gate` / `…_model_unavailable`), `PUT /categories/suggestions/hosted-consent`, `POST /transactions/{id}/suggestion/reject`; `GET /transactions/explanations` items gain `suggestion` (source always `model`).
