# WP 11.5b: The advisory catalogue (`catalogue/1`)

**Request (Chris, verbatim).** 2026-10-25: "Good with the llm proposal but I want to expand askpersonalfi to cover being a financial advisor so come up with an expansion proposal there without requiring a fine tuned model." 2026-10-26: "Good with proposal." WP 11.5b is row 11.5b of `docs/research/12-ask-personalfi-advisor-expansion.md` §6, under §2.1 ("Tools: the engines, exposed as a typed catalogue"), §2.3 and §4, serving 11 §3.2's "model as a compiler over a closed catalogue".

**Result.**

1. **Nineteen functions, `catalogue/1`.** Every function in 12 §2.1's table, each a thin wrapper over an engine, report, route or built-in rule that already exists, plus two pieces of arithmetic that did not exist: the **payoff amortisation** (D1 states the ordering and withholds the cost; WP 11.5a found it) and the **levers tornado** (07 §5.10; nothing computed sensitivities). `investing.tax_location` answers `not_available` (`engine_not_built`) with the reason: I12 has no engine.
2. **The gate is the query types' gate.** A function declares its scopes; it is listed and callable only when the holder's live grant to the narrator covers them. The grant is read by one new function, `narratorGrantCeiling` (`advisors/local/grant.ts`), which `insight.explain` (11.3) and `brief.narrate` (11.4) now also call. They used to inline the same expression, so there is now one code path, not three. An ungranted function is **absent from the listing**, and a direct call is refused 403. No function declares `transactions.raw`; the one built-in that needs it (U3) is left out of `recurring.waste` and named.
3. **Every figure traces.** A figure is `{money}`, `{decimal, unit}` or `{date}`, and each carries `source_refs` in the advisor contract's own form (`snapshot:<path>`).
   - `checkCatalogueResult` resolves every ref with the contract's own resolver (`resolveSourceRef`) against the result's own `inputs`. Those inputs are the scoped snapshot blocks, decimalised; the arguments; and any parameter, projection identity or contribution total the function read.
   - It refuses a figure with no ref, a ref that does not resolve, money or a decimal outside a figure, and any non-integer JSON number anywhere in the envelope.
   - A result that fails is never returned (`CatalogueResultRejected`).
4. **Versioned, described from the definitions.** `catalogueDescription()` emits JSON Schema (draft 2020-12) for each function's parameters and result, the shared envelope, and `$defs` for the shapes stated once.
   - It is published at `packages/contracts/advisor/catalogue/catalogue-1.json` (65 KB) and pinned twice: byte-for-byte against the file, and by digest (`CATALOGUE_DESCRIPTION_DIGEST`).
   - `node scripts/advisor-catalogue-gen.ts --check` (`pnpm run catalogue -- --check`) runs the same comparison outside vitest.
5. **Callable two ways.**
   - In process: `callCatalogue(dependencies, holder, name, args)`, typed by name for 11.5c/11.5d, or `callCatalogueByName`.
   - Over HTTP: `GET /advisor/catalogue` (what this holder can call) and `POST /advisor/catalogue/{name}`. Both are session-only, as `routes/insights.ts` reads are, because nothing is written.
   - OpenAPI regenerated: additive, +491 lines, no existing path changed. The gitignored web SDK was regenerated too.
6. **Read only and deterministic.** `plan.project`, `plan.compare` and `plan.levers` run the projection service's read and compute phases and **never its store phase**: no `projection_runs` row, no `ProjectionCompleted` event. The api-db suite counts the rows: 0 before, 0 after. Clock reads go only through the injected `Clock`; the only randomness is the seeded engines. The same call twice gives an identical result in every lane.
7. **Docs**:
   - RUNBOOK "The advisor's catalogue (v0.9.22)";
   - release notes `## v0.9.22`;
   - a pointer in 12 §6 row 11.5b.

**No migration, no query type, no prompt, no model call, no UI.** No live model or vendor was called.

**State of the tree.** Uncommitted, on `main` at `67bc608` (HEAD at the start; unchanged). Nothing is staged. `git status --short` was identical before and after the sabotage runs. The 16 phase-10 PNGs (4 modified `wp10.3-*.png`, 12 untracked `wp3.11-*.png`) are **not mine and were not touched**.

## 3. The payoff amortisation, against hand-worked cases

Method (`amortisation.ts`), month by month:

1. Interest accrues on every open balance at `balance × APR ÷ 12`, as integer minor units rounded half-even. A promotional rate applies to a month that starts before the promotion ends.
2. Every minimum is paid.
3. What is left of a **fixed** monthly budget (Σ minimums + extra) goes to one debt at a time in the chosen order; a debt that needs less passes the rest on in the same month.

**Rollover**: the budget is fixed at the start, so a cleared debt's minimum keeps flowing. A schedule still open after 600 months is `not_paid_off`. Avalanche orders by APR (ties: smaller balance); snowball orders by balance (ties: higher APR). Every case below was worked by hand before the code ran, and every one matched the code on its first run.

## 4. The tornado and its bound

`plan.levers` → `leverSensitivity` (Planning) re-runs the **baseline** once per declared step, on the **baseline's own seed** (common random numbers). It uses **the compare's path count**: `DEFAULT_MONTE_CARLO_PATHS` (10,000) when a Monte Carlo engine is bound, one deterministic path otherwise.

The steps are declared, never a caller's choice: retire one year later; save 2% more of income; spend 10% less in retirement; returns one point lower; claim Social Security one year later (never past 70); $10,000 a year of part-time income for three years; a $10,000 windfall on the plan's first day. Glidepath is skipped by design (`not_a_magnitude`: it is a choice of schedule). A lever the plan cannot move is skipped with its reason (`not_applicable`: no derived income for savings rate, no Social Security, already at 70). A lever the engine refuses is skipped with `refused`.

**The bound**:

- at most **eight runs** (the base and seven steps), each at the fixed path count;
- a **deadline of 20,000 ms** (`LEVER_SENSITIVITY_DEADLINE_MS`), read through the injected clock before each run;
- worst case: the deadline plus one run.

**When the deadline hits**, every lever not yet reached is reported `status: skipped, reason: deadline, detail: "not reached within the 20000 ms deadline"`. None is dropped. The result also carries `deadline_ms`.

Proof (`planning/test/catalogue-projections.test.ts`, with a fake runner that advances a mutable clock 6 s per run): the base ends at 6 s, and levers 1–3 run at 6, 12 and 18 s. The fourth would start at 24 s, so exactly four runs happen, and `expected_return_shift`, `ss_claim_age`, `part_time_income` and `one_time_windfall` are reported `deadline`.

The same tests show:

- eight runs, all on seed 424242 at 10,000 paths;
- ranking by |delta|, largest first, ties in 07 §5.10's order;
- determinism;
- a run on the real deterministic engine.

Over the real app with the real Monte Carlo engine, the api-db test that runs two tornadoes plus five projections took 8.2 s in total.

## 7. For the orchestrator, and choices Chris should know about

- **(a) The gate is the narrator's grant.** There is no catalogue-specific grant: the query types gate on the holder's grant to `local.narrator`, so the catalogue does too, through one shared function. When 11.5c/11.5d add a query type with its own manifest, they decide whether it reads this ceiling or its own.
- **(b) Read only.** `plan.project` and `plan.compare` compute when the cache misses and **do not store**. The plan screen's routes still store, so the same question asked there writes a run and asked here does not. Choosing otherwise would let a model's question write `projection_runs` rows and fire the goal-pace consumer.
- **(c) `limits.contribution_room` declares `cashflow.monthly`.** No existing scope is "contributions by account kind". This one crosses only month totals, the kind and the limit: no rows, dates finer than a month, or accounts. Adding a scope would need a contract bump and a CHECK migration, which this package was not to add. Chris may prefer a dedicated scope later.
- **(d) What counts as a contribution.** It is what `classifyActivity` (WP 10.3) calls a `contribution`, into accounts whose provider subtype is in the kind's list (IRA: `ira`, `traditional ira`, `roth`, `roth ira`; workplace: `401k`, `403b`, `457b`, `thrift savings plan`, `roth 401k`, `roth 403b`; HSA: `hsa`, `health savings account`). Excluded, with counts in the inputs: `TRANSFER_IN`/`GIFT_IN` and rollover/transfer/conversion subtypes; in-kind and unvalued rows; other currencies.
  - An employer match recorded as a contribution is counted, and the result's caveat says so.
  - The holder's age is not read, so catch-ups are listed, not added.
  - A manual account has no subtype until one is set.
- **(e) U3 is not in `recurring.waste`.** U3 reads `transactions.raw`, which is never a catalogue scope. Its finding still reaches the holder through the Brief and `insights.current`.
- **(f) `cash.emergency_fund`'s reference rate** is the parameter store's 3-month T-bill (cited by key), not `market.rates`. The api process has no FRED source, so the snapshot's `market_rates` block is always absent there.
- **(g) Declared steps.** The tornado's steps (§4) and `goal.required_savings`' default ceiling ($50,000 a month, echoed in the inputs) are constants of this package, not plan fields.
- **(h) Engine-backed figures cite the run identity.** A projection's figures cite the input digest, seed, method, paths and versions that reproduce them. A claim factor cites the engine's answer recorded in the inputs, beside the ages asked.
- **(i) The description is 65 KB** (two-space JSON; shared shapes under `$defs`). 11.5c may want a compact rendering for the compiler; it should be generated from `catalogueDescription()`, never hand-kept.
- **(j) A pre-existing warning, not mine.** `plan-routes.test.ts` and this suite both print one pg deprecation warning ("client.query() when the client is already executing a query") during goal creation. It is a pre-existing pattern on the goals path; it is not introduced here.
- **Commit together**: the definitions, `packages/contracts/advisor/catalogue/catalogue-1.json` and `openapi.json`.
