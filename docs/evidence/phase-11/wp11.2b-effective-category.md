# WP 11.2b: The effective category: what the automatic tiers decide now counts

**Request (Chris, verbatim).** 2026-10-27: "Dispatch 11.2b", approving the orchestrator's recommendation of the same date: _the ledger's effective category is `user ?? rule` only; tiers 3-5 (learned merchant default, provider PFC, classifier above its floor) are recorded in `category_assignments` but never reach the transaction list, the Inbox filter, budgets or reports. Make them effective with a provenance chip and the stored explanation ("Plaid", "learned from 4 confirmations", "classifier 92 %"), uncategorised only at tier 6; 04 section 5.2's "never silently apply" satisfied by the chip, the explain line and the floor; a holder's pick still wins._

**Result.** (1) The ledger owns a projection of the automatic decision: six nullable `transactions.auto_*` columns (migration 0058), written only by `setAutoCategories` and only for tiers 3-5; a rule's win or an all-tier abstention clears it; a holder's pick supersedes it and keeps it as history. (2) `resolveCategoryId(overlay, rule, auto)` is `user ?? rule ?? auto`, and every reader (list, detail, the `categoryIds` / `uncategorized` filters, budgets, the five reports, the insights category spend, the CSV export) gets the category through it or through one `COALESCE` pinned to it by a test. (3) A provenance chip ("Plaid", "Learned", "Classifier 92 %") on every automatic placement on `/transactions`, the detail sheet and `/categories/:id`, revealing the stored explanation by hover, press or Enter. (4) The Inbox's second queue, **Auto-categorised, unreviewed**, with **Looks right**, **Change** and a per-holder switch. (5) The projection is derived: the export omits it, the import re-derives it. No model call anywhere.

**State of the tree.** Uncommitted, as instructed. This package's files are listed in the final report; WP 11.3's (insights, health, narrator wiring, `0057`) were present beside them and were not touched, apart from the shared files named in section 6.

**Not done by design.** Not a ledger consumer of `categorization.AssignmentsChanged` (section 1.2 says why). No change to the engine's tier order, floor, calibration or `shouldReplace`. The dashboard's "To review" count is unchanged (it counts the first queue: uncategorised and transfer suggestions); the new section is advisory and is not in it. No backfill inside the migration (a job does it). The Inbox section orders by transaction date, newest first, within "placed in the last 30 days" (the list's keyset); it does not re-sort by decision time.

## 1. What was built

### 1.1 The projection: columns, not a table

`transactions` gets `auto_category_id`, `auto_tier` (`merchant_default` | `provider` | `classifier`), `auto_confidence NUMERIC(5,4)`, `auto_decided_at`, `auto_assignment_id`, `auto_superseded_at`, plus `users.inbox_show_auto_review`. Columns rather than a side table, for the reason 0004 and 0007 gave for the overlay and the rule tier: every reader of the effective category already reads `transactions` (the aggregate reports sum 50,000 rows in one pass), and a join on the hottest statements buys nothing the columns lack. History 04 section 5.2 wants kept lives in `category_assignments`; what stays on the row after a holder's pick is the machine's last answer, stamped `auto_superseded_at`.

```sql
ALTER TABLE transactions
  ADD COLUMN auto_category_id   UUID,
  ADD COLUMN auto_tier          TEXT
    CONSTRAINT transactions_auto_tier_check
    CHECK (auto_tier IS NULL OR auto_tier IN ('merchant_default', 'provider', 'classifier')),
  ADD COLUMN auto_confidence    NUMERIC(5, 4)
    CONSTRAINT transactions_auto_confidence_check
    CHECK (auto_confidence IS NULL OR auto_confidence BETWEEN 0 AND 1),
  ADD COLUMN auto_decided_at    TIMESTAMPTZ,
  ADD COLUMN auto_assignment_id UUID,
  ADD COLUMN auto_superseded_at TIMESTAMPTZ,
  ADD CONSTRAINT transactions_auto_whole CHECK (
    (auto_category_id IS NULL) = (auto_tier IS NULL)
    AND (auto_category_id IS NULL) = (auto_confidence IS NULL)
    AND (auto_category_id IS NULL) = (auto_decided_at IS NULL)
    AND (auto_category_id IS NULL) = (auto_assignment_id IS NULL)
    AND (auto_superseded_at IS NULL OR auto_category_id IS NOT NULL)
  );

CREATE INDEX transactions_auto_review_idx
  ON transactions (user_id, effective_date DESC, id DESC)
  WHERE auto_category_id IS NOT NULL
    AND user_category_id IS NULL
    AND rule_category_id IS NULL
    AND removed_at IS NULL;

ALTER TABLE users
  ADD COLUMN inbox_show_auto_review BOOLEAN NOT NULL DEFAULT TRUE;
```

(The file also carries two `COMMENT ON COLUMN`s and the header; the preference column is on `users` beside `dashboard_layout`, 0046's precedent.)

### 1.2 The write path: the pass's port, not a consumer

The brief asked for a ledger consumer of `AssignmentsChanged`. Built instead: `categorizeTransactions` hands the ledger its placements through `LedgerPort.writeAutoCategories`, on **its own transaction handle**, before it appends `AssignmentsChanged`. Reason: budgeting and recurring recompute "a deterministic function of current state" when that event arrives, and a third consumer writing the projection would race them (the pump delivers per consumer, in no order across consumers), leaving budgets' actuals computed from a ledger that had not yet been told. Written in the pass's transaction the projection is committed before any consumer can see the event, and an assignment and its placement cannot disagree after a rollback. The ledger still never imports the categorization context and never reads `category_assignments`; the composition root (`apps/api/src/domain.ts`) adapts the port to `setAutoCategories`, exactly as it does for `setRuleCategory`.

| Event in the pass                                            | Port call                                                                                     |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| tier 3 / 4 / 5 wins and is written                           | placement `{assignmentId, categoryId, tier, confidence (the stored NUMERIC(5,4)), decidedAt}` |
| a rule wins                                                  | `placement: null` (clear)                                                                     |
| every tier abstains and the row never had an assignment      | `placement: null`                                                                             |
| a holder's own pick (tier 1), a preview, an unchanged re-run | nothing                                                                                       |
| an abstention on a row that already has an assignment        | nothing (an abstention never demotes)                                                         |

`setAutoCategories` is idempotent per assignment id (`auto_assignment_id IS DISTINCT FROM`), refuses a tier that is not automatic (`ledger.invalid_auto_placement`, and the table `CHECK` behind it), is scoped to the holder, and never writes a stale `auto_*` back from a whole-row write: the sync update and the overlay write strip those columns (`withoutAutoColumns`), and a holder's pick sets `auto_superseded_at` by its own statement. `reprojectAutoCategories` (categorization) re-derives the same writes from the current assignments: the backfill for assignments that pre-date 0058 (the worker enqueues `categorization.project_auto` at boot, deduped), the self-heal, and the import's twin (`autoChangeOf` is the one mapping).

### 1.3 The resolver, and who reads it

| Tier | Source                                                                                  | Wins over              |
| ---- | --------------------------------------------------------------------------------------- | ---------------------- |
| 1    | `user_category_id` (a pick)                                                             | everything             |
| 2    | `rule_category_id`                                                                      | the automatic tiers    |
| 3-5  | `auto_category_id` (`merchant_default`, `provider`, `classifier` at or above its floor) | nothing; the last tier |
| 6    | none                                                                                    | uncategorised          |

`resolveCategory` also returns the tier (`categorySource`: `user` | `rule` | `auto`); only `auto` gets a chip. The SQL spelling (`effectiveCategorySql`, one `COALESCE`) serves the `categoryIds` and `uncategorized` filters and is pinned to the TypeScript by a test over all eight combinations of the three columns. Changes of meaning: `uncategorized` was `user_category_id IS NULL`; `categoryIds` matched the holder's column only (it now finds a rule's category too, as the reports' drill-through expects).

| Reader                                               | Through                                                  | Test                                                                                                                   |
| ---------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| transaction list, detail                             | `effectiveOf`                                            | api-db `wp112b-effective-category` "the list and the detail carry..."                                                  |
| `categoryIds`, `uncategorized`, `autoReview` filters | `effectiveCategorySql`                                   | api-db "the category filter, the uncategorised filter..."; ledger-db "the SQL COALESCE and resolveCategoryId agree..." |
| spending / income reports                            | `listAggregateSumsInWindow`, `listAggregateRowsInWindow` | api-db "spending and income reports count the placement..."; ledger-db "the aggregate rows and the grouped sums..."    |
| cash-flow hub, category history, spending pace       | the same aggregates                                      | api-db "the cash-flow hub, the category history and the spending pace..."                                              |
| budget activity, budget-vs-actual                    | budgeting port over `listTransactions`                   | api-db "the budget's activity and the budget-vs-actual report..."                                                      |
| budgeting port                                       | `createBudgetingLedgerPort`                              | api-db "the budgeting port, the insights snapshot's category spend and the CSV export..."                              |
| insights snapshot (category spend)                   | `createInsightsLedgerPort`                               | same test                                                                                                              |
| CSV export                                           | `listTransactions`                                       | same test                                                                                                              |
| bundle export / import                               | `DERIVED_COLUMNS`, `autoChangeOf`                        | api-db `wp112b-export-import`                                                                                          |

The classifier is held to its floor by the engine before it can win; `test/wp112b.test.ts` asserts a placement's confidence is at or above `DEFAULT_CONFIDENCE_FLOOR`, and that with the floor raised above what the model can reach nothing is offered.

### 1.4 Provenance, the Inbox, the preference

`GET /transactions` rows gain `categorySource` and `autoCategory {tier, confidence, decidedAt}` (the latter only when the machine's answer is the effective one); `GET /transactions/explanations` tiers gain the stored `facts` (a merchant default's `support`), so "Learned from 4 confirmations" is read off the stored chain; `autoReview=true` filters the review rows; `GET`/`PUT /inbox/preferences`. The web: `ProvenanceChip` (a real button in a popover: hover, press, Enter; Escape closes and returns focus; the row behind never hears the key), on its own line under the row so it cannot overflow the 320 px name cell; `AutoReviewSection` in the Inbox. The chip's figure is the api's stored one (`Classifier 92 %`); the line is the server's, read from storage, never composed client-side.
