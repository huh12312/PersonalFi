# Threat model — PersonalFi as built at `beaa8be` (v0.9 candidate)

**What this is.** 03 §1's STRIDE register (`docs/research/03-security-architecture.md`, written 2026-09-10 before any code), re-walked against the system as built. It adds the four surfaces 03 could not foresee: the local model, the weekly Brief, the production soak and the upgrade path. It also re-rates 03 §9's P0/P1/P2 checklist with evidence.
**By.** WP 9.10's external-style reviewer (it wrote none of the code). It reviews and records, never fixes.
**Read with.** `docs/security/asvs-assessment.md` (the ASVS 5.0 map) and `docs/evidence/phase-9/wp9.10-security-review.md`, where §2 has this review's sabotages, §3 the ZAP baseline and §5 the gap list. Gap ids `G-xx` and proposed accepted risks `A-xx` are defined in that §5.
**Scale.** As in 03: likelihood × impact, 1–5 each, for a single-user, self-hosted install with no public ingress. "Then" is 03's score. "Now" is the residual with the built controls in place.

TB-5 (app → sidecar) is now **TB-5′ (worker → local model)**: one-way and schema-validated. The model never sees a memo, an id or a row figure, and its output is data, never instructions. TB-8 (the upgrade's source of truth) is new.

## 3a. Provider API credentials stored by the product (WP 10.1, v0.9.1)

Until v0.9.1 the only way to give the install a Plaid client id and secret was the operator's secret files. The account holder can now enter their own in Add connection (migration 0041, `provider_credentials`; `docs/evidence/phase-10/wp10.1-plaid-credentials.md`).

- **What is sealed.** Both values, each a `SecretBox` envelope (XChaCha20-Poly1305 under a per-record DEK wrapped by the KEK, D5): the same custody tier as a Plaid access token. The AAD is `personalfi/v1 | provider_credentials | <client_id_sealed or secret_sealed> | <user_id>.<provider> | <key version>`, so a ciphertext lifted into the other column, another holder's row, or `connections.sealed_credentials` does not authenticate. The only plaintext derivative is the last four characters of the client id, for display. Removing the credentials retires the record's DEK, so a copy in an earlier backup cannot be opened either.
- **What a database dump plus the master key yields.** The Plaid client id and secret, exactly as it yields every Plaid access token today. A dump without the master key yields ciphertext. No new key custody tier, no new exposure beyond what a stolen dump and passphrase already give.
- **The step-up gate.** `PUT` and `DELETE` need a passkey assertion from the last five minutes (D21), like adding or removing a connection. A stolen session cookie can learn _whether_ Plaid is configured and the last four characters of the client id, and cannot read the secret (no route returns it), replace the keys or remove them. The worst replacement is the dangerous one: keys from an attacker's own Plaid account would make every bank the holder links afterwards belong to the attacker's Plaid dashboard. That is why a replacement is a step-up and is audited (`provider_credentials.set | .rotated | .removed` in `security_events`, with the environment and the four-character hint, never a value).
- **Where the secret travels.** Browser to api over TLS in one request body (the form clears its own copy before the request is sent), into the api process, where it is validated with a Link token request to Plaid (through `createPlaidApi`, the same client and the same TLS verification as the operator-file path, **G9-6**) and sealed. It is never logged (a planted canary is asserted absent from every log line, in-process and in the real-boot `log-hygiene` suite), never in an error message, a response or an audit row. While a client built from it is cached (30 s, or until a `ProviderCredentialsChanged` event) it sits in that client's request headers in api or worker memory, the same place the file path holds it for the life of the process.
- **Precedence and the production refusal.** Non-empty operator files win, and the product refuses to store a second set. `production` is refused unless `PLAID_ALLOW_PRODUCTION=true`, at write time and again at use time (D16).
- **Residuals.** (1) The audit row is written after the credential commits, not in the same transaction (`recordSecurityEvent` takes the pool, not a transaction handle); a crash between the two leaves a set credential with no `security_events` row, though the `ProviderCredentialsChanged` outbox event, which is in the transaction, still records the change. (2) The worker learns of a change through the outbox (seconds) or its 30 s cache expiry, so a removed key can serve a sync for up to 30 s. (3) A compromised api process holds the KEK and can read the row: the same as for access tokens (A-06, A-09). (4) Removing the keys revokes nothing at Plaid.

## 3b. The narrator on a hosted provider (WP 10.6, v0.9.5, D30)

**The data flow.** When — and only when — the holder ticks a hosted provider's consent in Settings, Language model, stores a key (or the operator writes `openai_api_key` / `openrouter_api_key` / `anthropic_api_key`), and makes that provider active, the worker's `insights.run_local` lane sends the narrator's request to it instead of to Ollama: the same minimised payload the preview showed and the holder approved (one Brief finding per call — its title, slotted summary, evidence labels, bucketed figures as slots, pseudonymised `MERCHANT_…` tokens; never a transaction, an account number or a raw merchant name), rendered by the same `renderPrompt`, POSTed over TLS from the worker's `backend` network to exactly one host per adapter (`api.openai.com`, `openrouter.ai`, `api.anthropic.com` — an egress policy built per adapter with that one host, https, port 443, DNS classified before the connect, redirects refused), with the holder's key in a header (`authorization` or `x-api-key`), opened from its `provider_credentials` envelope for the call and redacted from every provider string before a log line. The reply comes back through the same wrap and the same `validateResponse` as a local one (reply format, 1:1 match, numerals check); the run records `provider:model`, and the Brief names it on the narration. The api never narrates: its runtime renders and approves only, and its one outbound call is the Settings screen's Test, a fixed probe with no personal data. **What changes for the holder:** the minimised findings leave the machine for a third party under that party's retention and training terms; the consent text says so, a switch revokes the payload approval, and Off (or withdrawing the consent) stops it. **Residuals:** (1) a vendor sees the holder's IP-less but install-identifying API key and the request timing; (2) the hosted model is not digest-pinned — the vendor may change what serves a model id; the validator, not the model, decides what is shown; (3) the key in the operator's file is readable by every process that mounts it (api and worker), as the market-data keys are.

## 3c. The live evidence for the narrator controls (WP 10.16, v0.9.15)

The controls above are proven in CI against fakes; since v0.9.15 they are also proven **against the live install**, on demand, by the GenAI controls self-test (Settings, Language model, **Run control checks**, or `just genai-selftest` from the host; RUNBOOK [Proving the GenAI controls](../../RUNBOOK.md#proving-the-genai-controls)). With the holder's own passkey it asks the running system, in order: whether a narration with no live approval is refused `payload_not_approved` without reaching the model (inside a transaction that is rolled back); whether a level-4 cancel ends a probe run within 2 s and closes the adapter's connection (the adapter's abort counter, not a log line); whether a reply carrying a number the finding never had, and a reply outside the reply format, are refused by the unchanged validator; whether the adapter's egress policy refuses an unlisted host before any connect; whether withdrawing the active provider's consent turns the narrator Off and forces a fresh consent and approval (rolled back); whether the last narration's retained payload re-digests (C5-5); whether the hosted window counted every probe at 30 calls an hour; the kill switches' state; whether the Brief's badge names the provider and model the payload was approved for; and, for the local model, whether the served digest is the pin. Each run writes a dated `ops_control_checks` row (migration 0052) of facts in words — never a payload, prompt, key or reply — and the dashboard's backup line says when the controls were last proven. A check that cannot run is recorded as skipped with its reason, never as a pass. The self-test is evidence, not a control: it adds no path to a model (the api still has none; the probes run in the worker through the narration's own adapter) and spends at most three hosted calls of the holder's window.
